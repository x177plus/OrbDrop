## 1. 致命 Bug（P0）

### ✅ P0-1 推送接收的落盘根用对端自报的设备名拼接，未做清洗 → 可写到下载目录之外

**问题**
- `transfer/download.rs:633`、`transfer/push_job.rs:830`：`config.download_dir.join(&invite.sender.name)`。
- `sender.name` 直接来自报文：`server/routes_push.rs:88-100`（HTTP）与 `ws/session.rs:147-154`（WS，未知设备时回落到线上名字），无任何校验、无长度上限。
- `Path::join` 对"带盘符前缀/绝对路径"的入参会**清空**已累积基址。`[实测]` rustc 探针：`base.join("C:\\Windows\\Temp")` → `C:\Windows\Temp`；`base.join("C:foo\\bar")` → `C:foo\bar`；`base.join("\\\\?\\C:\\Windows")` → 原样；`base.join("..\\..\\..\\Users\\Public")` → 逐级逃逸。
- 第二道口子：`transfer/resume.rs:210-218` 的 `safe_join` 只挡 `..`/`.`/空段/反斜杠，**不挡盘符前缀**。`[实测]` `safe_join(root,"C:/Windows/Temp/x.txt")` → `C:Windows\Temp\x.txt`（基址同样丢失）；`safe_join(root,"C:foo/x")` → `C:foo\x`。

**隐患**：已配对设备**免同意自动接收**；未配对设备只需用户点一次「接收」。拿到这条路径即可向任意可写位置（含开机启动目录）写文件并覆盖同名文件 —— 本机任意文件写入。与 `docs/requirements.md:412` 写死的"一律收在 `<下载目录>/<发送方名>/` 下面"冲突。

**修法**
1. 净化对端名字：只保留合法文件名字符，去掉分隔符/盘符/`..`/结尾点与空格，限长；净化后为空退 `unknown-device`。
2. `safe_join` 增加"每段必须是纯文件名"的校验（拒绝带前缀、以分隔符开头、以 `.` 结尾等）。
3. 落盘前做最终断言：目标路径必须以 `<下载目录>/<净化后的名字>` 为前缀。
4. 回归测试：`C:\…`、`C:foo`、`\\?\…`、`..\`、`a/C:/b`、`CON`、`x. ` 等输入必须被拒或落回基址。

### ✅ P0-2 CFAPI 目录展开：三个数组各自过滤后按下标混用 → 名字/身份错配，或越界 panic（进程退出）

**问题**：`mirror/win.rs:585-624`
- `names`（经 `plain_component` 过滤）、`blobs`（`encode()` 失败即丢）、`entries`（未过滤）三份独立过滤，随后 `entries_used = names.len()` 并按下标取 `entries[i]` / `blobs[i]`。
- 数量不一致时只 `warn!`，继续执行。

**隐患**
- 任一名字被判非法（macOS 侧 `...`、空白名等）→ 本地名与远端身份 blob 错位 → 目标复制到**别的文件**的字节，或给文件建出目录占位符。
- 远端路径 > `IDENTITY_MAX`(4096) 使 `blobs` 变短 → `blobs[i]` 越界 panic，位置在 `unsafe extern "system"` 回调内 = **整个进程退出**，触发点为资源管理器枚举该目录。

**修法**：过滤合并为一次（`filter_map` 产出 `(本地名, blob, 元数据)` 三件套，要么全留要么全丢）；数量不一致直接 `fail_placeholders` 返回；回调内加 `catch_unwind` 兜底。

### ✅ P0-3 BC 集成唯一入口（回环 `/proxy/<设备id>/`）的 OPTIONS 被 CORS 层抢答

**问题**
- `bc.rs:239/723` 写入 profile 的 BaseURL 是 `server::proxy::base_url(...)` = 本机回环 `/proxy/<设备id>/`。
- 该路由落在挂了"放开所有来源/方法/头"的 CORS 层那张路由表里（`server/mod.rs:89-92` 定义、`:175-207` 挂载）；只有 `/dav` 被特意排除（`:209-232`，注释原文：「被抢答就等于『这不是 WebDAV』，远端目录在 BC 里直接加载不了」）。
- tower-http 的 CORS 会抢答**所有** OPTIONS，不向后传递。
- `[实测]`：`OPTIONS /proxy/peer-x/`（带不带 Origin 都一样）→ `200`，仅 `access-control-allow-methods: *`，**无 `DAV:` 头**；同一进程中 `OPTIONS /dav/<shareId>/` → `dav: 1,2` + `Allow:` 列表。

**隐患**：BC 拿不到 DAV 能力协商结果，远端目录很可能加载不出来（`[推断]` BC 端行为，未驱动真机）；症状表现为"BC 打不开对端"，根因难定位。

**修法**：把 `/proxy/*` 移出 CORS 层（与 `/dav` 同法单独成表），或让 CORS 层只作用于本机 UI 用到的前端路由。改完必须用真机 BC 走一遍"从 profile 打开对端目录"。

### ✅ P0-4 本机共享项的右键「下载到本地 / 打开所在文件夹 / 复制共享路径」是假成功桩

**问题**：`src/App.svelte:1917-1926`（`ctxDownload`/`ctxOpen` 只 `toast`）、`:1942-1945`（`ctxCopy` 只 `toast`，未写剪贴板；同文件另三处复制都写了 `navigator.clipboard.writeText`）。后端命令与前端封装齐备：`lib.rs:1439 download_file`（含 S-02「每次弹窗选位置」）、`lib.rs:1488 download_and_open`、`api.ts:320/328`。`[代码]` 全仓搜索确认 `src/` 内**零调用点**。

**隐患**：提示"已开始下载到下载目录"，实际不产出文件；「打开所在文件夹」提示在访达中打开（Windows 上文案也错）却什么都不发生；S-02 的弹窗路径永不触发。F-40/F-44（均 P0）本机侧实际不可用。

**修法**：三个函数接到已有命令；本机项「打开所在文件夹」用 `open_path` 打开共享项所在目录；复制改用 `clipboard.writeText`；补错误提示。

## 2. 一般 Bug（P1）

### 安全类

**✅ P1-1 清空全部凭据后旧 token 仍可用** — `credential.rs:512-519` 的 `wipe()` 删文件但**不**让派生缓存失效（失效只靠 `write_vault` 里的版本号自增 `:279`），而 `ws/session.rs:116` 的认人走缓存。隐患：用户点完 F-15，被删 token 仍通过认证，对端自动重拨几秒内被接受（并写回 `autoConnect`），HTTP/DAV/推送照旧放行，直到下一次任何写凭据动作。修法：`wipe()` 同样自增版本号，并加测试断言 wipe 后旧 token 查不出来。 **✅ 已修**：`wipe()` 无论删没删成功都自增版本号（认人缓存立刻失效）。测试 `credential::tests::wipe_invalidates_the_derived_token_cache`（含"文件已不在"那一档）。

**✅ P1-2 长连接上的 Unpair 可踢掉任意第三方设备** — `ws/session.rs:269-276` 用报文里的 `who` 而非会话已认证的 `peer_id`。隐患：任一已配对对端可删另一台设备的凭据、断链、移出地址簿。修法：忽略报文 id，改用会话身份；不一致即丢弃。 **✅ 已修**：`Unpair` 只认会话身份，报文里的 id 与它不一致就丢掉。测试 `ws::session::tests::unpair_over_ws_only_acts_on_the_session_identity`。

**✅ P1-3 回环免认证 + 放开所有来源的 CORS** — `auth.rs:55-57` 对 `127.0.0.1` 直接给 `Caller::Local`；`server/mod.rs:89-92` 放开全部来源/方法/头。`[实测]`（无凭据）：`GET /shares` 200 列出共享项、`GET /file` 200 读文件、`PUT /dav/<id>/injected.txt` **201**、`DELETE /dav/<id>/a.txt` **204**、读回成功。隐患：本机任意进程可枚举并删除/覆盖共享文件；可访问回环的网页同理（较新 Chrome 的 PNA 会拦，Firefox/Safari 目前不拦）。修法：回环分支增加额外门槛（每次启动随机、仅本机前端知晓的头，或 Origin 白名单）；CORS 收窄到自己的 origin。 **✅ 已修**：CORS 收紧成"只回本机来源"（`server::is_trusted_origin`），带**外来 Origin** 的回环请求不再算 `Caller::Local`（要凭据）。测试 `server::tests::{loopback_needs_no_token_but_a_foreign_origin_does, only_local_origins_are_trusted}`。

**✅ P1-4 `/push/report` 无认证** — 公开路由 + `routes_push.rs:163-195` 只认 `invite_id`（v4 UUID），而 `/push/download` 会复查配对状态。隐患：伪造 `push_done` 可把在途传输判完成/失败。修法：加与 `/push/invite`、`/push/download` 同一套身份校验。 **✅ 已修**：`/push/report` 与 `/push/invite`、`/push/download` 共用同一道 `authorize`（已配对的对端必须出示 token；未绑定仍只认 invite_id）。测试 `server::routes_push::tests::push_report_needs_the_token_of_a_paired_peer`。

**✅ P1-5 配对码无节流** — `routes_pair.rs:122-135` 无延迟/计数/锁定，`CODE_TTL = 120s`，码空间 9e5。隐患：局域网内可暴力试出（用户正在显示码时被陌生设备配上）。修法：按来源限流 + 连错作废当前码。 **✅ 已修**：`PairStore` 按来源地址记猜错次数（5 次/分钟 → 429，猜对清零）。测试 `server::routes_pair::tests::pairing_code_attempts_are_throttled_per_source`。

**✅ P1-6 配对邀请的身份闸门可被诱导打开** — `routes_pair.rs:208-209` 的 `known_broken` 取 `state.ws.needs_repair(peer_id)`（"我方拨号被 401/403 或指纹不符"）。隐患：同网段者可先制造拨号失败、再免 token 用该 id 发邀请，邀请被送进用户通知（卡片标 `unproven`，仍需用户点「接收」，属削弱而非完全绕过）。修法：把该状态仅用于"允许重新配对"，并在卡片上明示身份未校验、加频率约束。 **✅ 已修**：`known_broken` 那条例外留着（否则正常的重新配对会被静默 401 挡掉），但加了频率约束 —— 同一个 peer id 每 120s 只放行一条"无凭据邀请"，再多就 429；卡片上的"身份未经校验"提示本来就有（`unproven`）。测试 `server::routes_pair::tests::a_repairing_peer_invite_reaches_the_user_instead_of_401`（正常路径仍通）。

**✅ P1-7 群聊三处缺成员校验** — `group.rs:651-700`（`apply_roster` 不校验发送者，更大 `rev` 即胜 → 名册劫持）、`group.rs:1932-1945`（`on_sync_ask` 只校验本机自己是否成员 → 可拉走 200 条消息 + 完整名册）、`group.rs:1724-1737`（`on_group_text` 只要求自称作者是成员 → 可冒名发言）。隐患：群被夺权、历史外泄、伪造消息，且不需要先配对。修法：名册/消息/补拉/回执统一校验"发送者是当前成员"。 **✅ 已修**：三处统一成"发送者必须是成员" —— 名册用**本机手上那份**名册判（自己退群那一档也成立）、陌生群要求发送者出现在它自己送来的名册里、补拉要求问的人是成员、群消息要求**信封发送者**是成员（挂着的邀请卡上的成员也算，F-97 的"先攒着"不受影响）。测试 `group::tests::{a_foreign_peer_cannot_rewrite_a_known_roster, an_unknown_group_roster_from_a_non_member_never_shows_a_card, a_foreign_peer_gets_no_history_and_cannot_post}`。

### 正确性类

**✅ P1-8 空文件经 DAV 输出 `content-length: 1` / 正文 0 字节** — `routes_dav.rs:422`（`end - start + 1`）配合 `:457-460`（`total == 0` 时得 `(0,0)`）。`[实测]` 同文件走 `/file` 正常，走 `/dav` 时 curl 直接失败（`transfer closed with 1 bytes remaining to read`）。隐患：BC 保存被清空的文件、读空文件都会失败。修法：`total == 0` 时长度为 0，补 0 字节 GET/HEAD 测试。 **✅ 已修**：`total == 0` 时长度取 0（旧写法 `end - start + 1` 对空文件算出 1）。测试 `server::routes_dav::tests::an_empty_file_is_served_as_zero_bytes`（GET/HEAD 都是 0，非空文件照旧 1）；真机 `[实测]`：`GET /dav/<id>/empty.txt` → `content-length: 0` 且 curl 退出码 0（修之前是 `content-length: 1` + curl 报 `transfer closed with 1 bytes remaining to read`）。

**✅ P1-9 并发接收的块计数非幂等 → 收全了也判失败** — `download.rs:206-221` 的 `done_blocks/received` 无条件自增，而 worker 对同一批任务会重试（`:1016-1046`）→ 断流重试后计数超总数，成功判据（`+1 == total`、`:888` 兜底）永不成立，文件报"没有收到全部数据"且停在 `.part`。同源：`:1041-1046` 在 bundle 重试失败时把已收全的成员一起 `mark_failed`，而 `:883-893` 跳过 failed → 永不 finalize。修法：完成动作幂等（位图已置位则不计数）；重试失败只标未收全的成员。 **✅ 已修**：`complete_block` 幂等（位图已置位就不计数 —— 重试重发同一批块时 `done_blocks` 不再超过总块数）；新增 `fail_task_files`：任务重试到底失败时**只标没收全的文件**（收全但没走到 `END` 的那些交给收尾兜底扫描，不再被跳过）。测试 `transfer::download::tests::{a_retried_block_is_not_counted_twice, only_incomplete_files_are_failed_when_a_task_dies}`。

**✅ P1-10 群聊补拉门闩永不重置** — `group.rs:1033-1057` 的 `rounds` 普通请求也自增，唯一清零点是 `GroupSyncPost` 返回（`:1984`）；`reachable()`（`:2020-2024`）把"有地址但离线"也算可达，60s 兜底扫每轮 +1 → 约 6 分钟后该 `(群, 设备)` 的补拉**永久失效**（进程重启才恢复）。隐患：F-99 的"必然收敛"静默失效。修法：`rounds` 只对追补轮次计数，超时/对方上线/收到其消息时复位。 **✅ 已修**：`SyncGate.rounds` 改成 `chase_rounds` —— **只有追批占额度**，普通一问（用户点、链路恢复、60s 兜底扫）把这一串清零，不再"6 分钟后再也不问"。测试 `group::tests::repeated_sweeps_never_lock_the_sync_gate_shut`（拨快时钟跑 20 轮兜底扫；回退后第 6 轮就失败，正是这个 bug）。

**✅ P1-11 被裁剪的历史被当成永久缺口** — `group.rs:1175-1214`：`holes_in` 把 `1..=max` 的空缺都当洞，而 `MAX_PER_GROUP = 500` 有意从最老那头砍。隐患：顶部常驻假告警「有 N 条消息未能同步」+ 每条消息触发一次补拉（3s 冷却的持续后台流量）。修法：记录每个发送者"已裁剪下界"，只在其上找洞；界面区分"真缺失"与"本地裁剪"。 **✅ 已修**：`GroupConvo` 新增 `pruned_below`（每个发送方被本地裁剪的下界，跟着 `prune` 记录），`holes_in` 从下界之上开始找洞 —— 被裁掉的老号不再被当成永久缺口。测试 `group::tests::pruned_history_is_not_reported_as_a_hole`（回退后立刻报 120 个假洞）。

### 资源 / 平台类

**✅ P1-12 文件变更监听：防抖写反 + 取消后任务空转** — `share/watcher.rs:77-86` 每轮新建 300ms `sleep`，任何事件取消它（实际是"每次事件归零"，与注释相反）→ 大目录复制期间远端不刷新（F-33 打折）、`pending` 无界；`rx` 关闭后 `Some(event)` 不再匹配、sleep 分支空转（每次 add/remove 共享项泄漏一个 4Hz 任务，违背 N-04）。修法：固定 deadline 防抖 + `None => break`。 **✅ 已修**：`share/watcher.rs` 抽出 `debounce_loop` —— 攒批窗口只在**第一批**起算（后续事件不推后）、通道关闭即退出，另加 `MAX_PENDING` 上限（丢最老的）。测试 `share::watcher::tests::{a_window_batches_and_dedupes, a_long_burst_still_emits_batches, pending_is_capped_from_the_old_end}`（"通道关闭必须收工"那条正是旧实现的空转泄漏；旧写法在持续变更期间一批都发不出来）。

## 3. 小问题 / 隐患（P2）

### 持久化与身份
- 配置损坏即换 `device_id`（`config.rs:684-693` 改名后写默认值）→ 对端看到"同一地址的新设备"，多出一行、共享项/地址簿全丢。修法：从 `.toml.bad` 里回收 `device_id`（最好连共享项/地址簿）。
- `config.toml` 写盘非原子（`config.rs:710-717` 用 `std::fs::write`）→ 崩溃得到半截文件，进而触发上一条。修法：改用 `write_atomic`。
- `identity.pem` 未设 0600（`net.rs:143-150`，凭据文件设了）→ 同机其他用户可读私钥冒充本机。修法：写后补权限。
- mDNS 缺 `id` 的公告会建空 id 设备行（`discover/mod.rs:118-150` + `lib.rs:1786`）。修法：过滤空 id（其他发现路径已这么做）。
- 端口探测多试一个 3900（`server/mod.rs:322-345`），S-06 写的是 3891-3899。修法：对齐其中一边。
- 「手动添加设备」不受离线/隐身约束（`lib.rs:722-735` 缺 `ensure_online`）。修法：补同一道门。

### 服务端 / DAV
- 隐藏文件过滤不一致（`/tree`、`/shares` 跳过 `.` 开头；DAV 目录列表不跳过）→ 计数与 BC 所见不符，且隐藏文件可经 DAV 下载。
- DAV 的 PUT 无 body 上限（`routes_dav.rs:513`，上限只挂 `/push/*`）→ 可写满共享方磁盘。
- PROPFIND 在 async 中调用 `std::fs::metadata`（`routes_dav.rs:252`）→ 大目录占住运行时线程。
- `resolve_within` 一律拒绝含 `:` 的路径段（`routes_dav.rs:132`）→ macOS 合法文件名被 403；且返回未 canonicalize 的 `candidate`（`:135/156`），共享项内已存在的悬空符号链接可被写操作跟随出沙箱。
- 代理通配路径未限制在 `/dav/`（`proxy.rs:51-53`、`:190`）→ 持该设备 token 的回环调用方可把代理当中继打到 `/unpair`、`/discover`。
- token 比较非常量时间（`ws/session.rs:116`、`proxy.rs:98-121`）→ LAN 上不可实用，记录在案。
- 需求 §5.3 的 `PUT/DELETE /file`、`POST /share/permissions`、`POST /push/respond|confirm` 现实中不存在（`[实测] PUT /file` → 405）；F-73 因此没有可挂的接口。
- DAV 细节：共享项根是文件时 href 仍带尾斜杠；忽略 `If-None-Match`/`If-Modified-Since`；语法错误的 Range 返回 200 而非 416。

### 传输
- 接收端无 `xxx (1).ext` 去重（`download.rs:280` 直接覆盖）→ 下载目录内同名文件被静默替换（S-01 与需求风险表两处口径不一致）。
