# 拖拽下载的第二条实现：CFAPI 镜像（本地真实路径 + 按需从对端拉）

> 版本：2026-09-22　状态：**核心链路已端到端验证**（占位符 → 目标读 → 拉对端 → 字节一致 →
> 按需填充目录），**开关默认关**；实机拖放手势（OLE 拖到资源管理器/微信）尚未由人手验证过。
> 本文记的是"靠实验才逼出来"的事实，改动前先读第 3 节，别按直觉写。

## 1. 它解决什么

F-46（把共享项拖到任意应用里）原本有两条路，各有一个硬伤：

- **提前转存**（小项先整份下到 `<数据目录>/staging/<uuid>`）：起拖前必须等内容下完（用户得按着
  鼠标等），被抓起来就下、取消/落空也下完且留 6 小时，而且 1 GiB 就是 1 GiB 真实磁盘。
- **虚拟文件**（`CFSTR_FILEDESCRIPTOR` + 自定义 `IStream`）：秒起拖、不落盘，但只有资源管理器 /
  Chromium 系 / QQ 这一小撮实现认它 —— 只认 `CF_HDROP` 的应用（微信这类）**什么都收不到**。

镜像这条路把两者合并：**抓起只在本地建一个占位符（0 字节、0.2 ms），交给目标的是真实路径；
字节等目标真的去读它的时候才从对端拉**。等待发生在目标进程里（它的读被内核挂起），我们自己的
窗口和拖放循环早就结束了。

代码：`src-tauri/src/mirror/`（`identity.rs` 身份 blob 与路径映射、`win.rs` CFAPI provider、
`mod.rs` 生命周期与回收），入口在 `drag::prepare_peer_payload`（`ORBDROP_DRAG_MIRROR=1` 时优先走
它，失败退回旧路），启动/退出挂在 `lib.rs`。

## 2. 实测数值

条件：Windows 11 Pro 26200、C: NTFS、Defender 默认开、**普通用户上下文（无提权）**。

| 操作 | 数值 |
|---|---|
| `CfRegisterSyncRoot` | 1.53 ms |
| 建 1 个目录占位符（抓起那一刻） | 0.22 ms |
| 建 1 个文件占位符 | 0.25 ms |
| 批量 2,000 个占位符（一次调用） | 124.8 ms（62 µs/项） |
| 批量 10,000 个（一次调用） | 843 ms（84 µs/项） |
| 真实树 100 目录×100 文件（101 次调用） | 723 ms（72 µs/项） |
| 对照：同样形状用**真空文件**建 | 2,777 ms（275 µs/项） |
| **1 GiB 占位符的磁盘占用** | **0 字节**（逻辑大小 1 GiB、"磁盘上的大小" 0） |
| 占位符的元数据开销 | ≈ 0.29 KiB/项（10,100 项 = 2,936 KiB） |
| `CfUnregisterSyncRoot` | 5 项 13 ms / 2,201 项 388 ms / 10,100 项 1,928 ms（≈0.19 ms/项） |
| 一次 `/tree`（目录内 100 项，debug、进程内） | p50 2.00 ms |

对照：真写 1 GiB 到磁盘 = 1.96 s + 1 GiB 空间。

## 3. 实测逼出来的事实（每一条都踩过）

### 3.1 provider 不常驻，镜像里的东西就读不了

不连 provider 读一个占位符得到 **`os error 362`（云文件提供程序未运行）**。所以：

- 拖放源**只给 `DROPEFFECT_COPY`** —— 落点是目标自己复制的真实文件，不依赖我们；
- 退出必须收摊（见 3.6）；启动必须自愈（见 3.7）。

### 3.2 目录占位符**也必须带身份 blob**

不带的话：`CfCreatePlaceholders` 每条 entry 的 `Result` 都报 `S_OK`，**整体却返回
`0x8007017C`（云操作无效）**，而且那个目录**访问不了**（`metadata` 直接失败）。
一个会骗人的失败模式 —— 所以逐条结果也要看，别只看整调用。

### 3.3 `RelativeFileName` 只能是**单段名字**

给 `not-there/child.bin` 会得到 `0x8007007B`（文件名、目录名或卷标语法不正确）。于是：

- 建树是"一个目录一次调用"，父目录必须先真实存在；
- 自己的身份 blob 里存的远端路径段必须用**原始**名字（对端按它找文件），本地落点才用清洗过的
  （`peer_fs::plain_component`）。

### 3.4 平台**不会**为 provider 自己进程的枚举做按需填充（关键）

从本进程 `read_dir` 一个"未填充"的目录占位符 → 拿到空的本地视图，**`FETCH_PLACEHOLDERS` 根本
不进来**（我们在 5 秒内轮询了 50 次，一次回调都没有）。换成**另一个进程**（测试里用
`cmd /c dir`）→ 回调立刻到，条目一次给全。

含义：真实场景里枚举者是资源管理器/目标应用，**那条路是通的**；但我们自己（或任何跑在本进程里的
代码）看镜像目录是看不到内容的。写回归测试时必须用子进程枚举，否则测的是一个假象。

### 3.5 填充策略选 `FULL`，不是 `PARTIAL`

我们的处理器每次都把**整层**拉回来、并顺手用 `DISABLE_ON_DEMAND_POPULATION` 声明"这一层齐了"，
所以每个目录只需要一次回调。`PARTIAL` 是"平台按应用实际要的条目来问"，野生目录列表会让同一个
目录被反复问（官方文档原话：*potentially 100+ times*），而每问一次我们就要重新 `/tree` 一次。

水合策略是 `PROGRESSIVE`（目标读到哪段给哪段，其余在句柄还开着时继续拉）；`FULL` 是"整份到齐才
放行"（大文件就是长时间卡住），而 `ALWAYS_FULL` 直接不可选 —— 平台会拒绝 `CfCreatePlaceholders`。

### 3.6 交付数据的两条硬规矩

- **offset 与 length 都必须是 4 KiB 的倍数**，除非这一段结束在文件末尾（末尾那一段不要求对齐）。
  对端文件比占位符记录的小（远端被改过）会让这条不成立 —— 那种情况必须**报错**，不能交一段错位
  的字节。
- 失败必须用 `STATUS_CLOUD_FILE_*` 里的状态回报（其它状态会被平台一律折成 `UNSUCCESSFUL`）。
  **绝不能报成功**：那会让目标拷出一份静默残缺的文件。

### 3.7 `CfGetSyncRootInfoByPath` 的缓冲区：`STANDARD` 是 1 KB 级的

实测：`STANDARD` 给 512 字节 → `0x800700EA`（`ERROR_MORE_DATA`）；给 4096 → 成功，返回长度
1056；`BASIC` 只要 8 字节（`SyncRootFileId`）。

这条坑的后果很隐蔽：只看成败的调用方会把 `ERROR_MORE_DATA` 读成"**没注册**"，于是**启动时每次
重复注册、退出时又跳过注销**，在本机留下"有注册、没 provider"的残骸（实现里真踩过：六个失败的
测试运行留下六个注册，得手动注销）。现在一律用 `BASIC` + 32 字节缓冲。

### 3.8 注册/注销的账

注册很便宜（1.53 ms），注销是 **O(N)**（10,100 个占位符 1.9 s）。所以生命周期是
**退出清干净、启动从头建**：退出 = 断开 → 删镜像树 → 注销（先删树把注销压回常量级），
启动 = 注册 + 连接。镜像里的一切都能从对端重建，留着只会留下没人能水合的残骸。

### 3.9 注册时必须带 `CF_REGISTER_FLAG_DISABLE_ON_DEMAND_POPULATION_ON_ROOT`（否则"拖了没反应"）

**这是实机上唯一一次"任何拖动都没有文件出现"的原因。** 不给这个标志时，平台会把**镜像根自己**
当成"未填充目录"来问我们要内容（`FETCH_PLACEHOLDERS`），而根是我们 `create_dir_all` 出来的普通
目录、没有身份 blob —— 我们只能判失败，于是**整个同步根在目标眼里变得列不出来**：

```
WARN 回调没带身份 blob file_id=... path=...\OrbDrop\mirror size=0     ← file_id 每次都一样（根）
WARN 把这次目录枚举判失败 {'why': '身份解不出来'}
```

资源管理器在落下时要把 `CF_HDROP` 给出的路径解析成 shell 条目，途中撞上这个根 → 它认为
落点不可用 → **什么都不复制**（症状与"拖动被吃掉"一模一样，但日志里 `拖拽已落下 effect=1` 是有的）。

复现与回归都放在 `tests/mirror_hydrate.rs`：用**子进程**（`cmd /c dir`）分别列
`<镜像根>`、`<镜像根>/<peer>`、`<镜像根>/<share>` 三层，每层都必须列得出来 —— 修复前第一层就挂。

另外：**注册是持久的，改策略必须走 `CF_REGISTER_FLAG_UPDATE`**。只在"未注册"时才注册的话，
上一版留下的旧标志会一直生效（症状照旧）。所以启动时若发现已注册，就用 UPDATE 刷新一遍。

### 3.10 水合之后本地会留着字节

读完 3 MiB 的占位符后，"磁盘上的大小" = 3,146,962 字节（真实占用）。我们开了
`AUTO_DEHYDRATION_ALLOWED`，平台**可能**随后自己脱水把它收回去（观察到过一次 0 字节）——
所以"水合后一定占着盘"这句话不成立，别拿它做断言。

回收是两条路：目标关掉最后一个句柄 → `NOTIFY_FILE_CLOSE_COMPLETION` 记账 → `mirror::sweep`
在 60 秒 grace 之后删；兜底是 6 小时按龄扫。**不做"拖完就删"** —— 资源管理器可能在
`DoDragDrop` 返回后还在异步复制。

### 3.11 镜像里的东西**不能**被共享 / 不能被推送

镜像里放的是占位符：对端拿到的是一个读不出内容的空壳（内容只在我们进程活着时才读得出来），
当推送源同样没有意义。实机踩过：把镜像里的文件拖回面板 → 它成了一条共享项 → 接着
`share::watcher` 去挂 watcher（占位符挂不上，日志一行 `Input watch path is neither a file nor a directory`）。

拦在四处，两条判据（都在 `unsendable`）：

| 判据 | 范围 | 用在哪 |
|---|---|---|
| `is_own_data_path` | 数据目录**整棵子树**（含 `credentials.dat`、`identity.pem`、`config.toml`、镜像） | 添加共享项、推送顶层源、推送走查 |
| `is_mirror_path` | 镜像子树 | 同上，**排在前** —— 只为把话说具体（"镜像目录…"，对得上用户刚做的事） |

| 位置 | 行为 |
|---|---|
| `add_share_impl` | **报错**："镜像目录（拖放用的本地占位符）不能添加为共享项" / "OrbDrop 自己的数据目录不能共享（里面是本机的设置与凭据）" |
| `fs_browse` 列目录 | 数据目录**本身**不列出（`is_own_data_dir`，保持原约定）+ 镜像子树不列出（机器中间产物不该出现在选择框里） |
| `transfer::manifest_for_paths` 顶层源 | **报错**（同上两条消息） |
| `collect_dir_manifest` 走查 | 跳过并计数（`is_own_data_path`） |

`credentials.dat` 是真正的靶子：它不是数据目录本身、也不在镜像里，**只挡那两条会把它放过去**，
而一条共享项加一次推送就等于把整台机器的配对凭据交给对端（`is_own_data_path` 这条就是为它加的）。

前端 `App.svelte::addShares` 同步改了一处：一条都没成时把**后端给的原因**说出来 —— 否则用户看到
的只是一句"没有添加任何共享项"，对着一次沉默的拒绝发呆。

### 3.12 水合的 HTTP 客户端必须**建一次复用**（每段新建 = 每段一次 TLS 握手）

真机数据（你的那次：拖一个 776 MB 的文件到资源管理器，千兆内网）：

```
共 725 个 1 MiB 区间   min=16ms  中位=41ms   max=261ms   → ≈24 MiB/s
```

同一台机的环回对照是 ~108 MiB/s，所以差额不在带宽 —— 而在**每个区间回调都新建一次 reqwest
客户端**（＝每次重新 TLS 握手）。改成连接建立时建一份、所有区间复用（环回 A/B：每段 8–9 ms →
对照组 11–37 ms，单段最高 42 ms）。现在日志里启动时只有一行
`水合用的 HTTP 客户端已建（后续所有区间复用同一条 TLS 连接）`。

顺带说明：资源管理器是**按 1 MiB 一段**读的（不是我要的 4 MiB），所以 `READ_CHUNK` 只是上限，
真实粒度由平台决定。

## 5. 怎么验

```bash
# 端到端（真同步根 + 真 HTTP，跑完自己收干净；失败也收 —— Drop 守卫）
cargo test --test mirror_hydrate -- --nocapture

# 实机：启动后日志里应当看到"同步根已就绪/已注册" + "同步根已连接（镜像可用）"
RUST_LOG=orbdrop_lib=info cargo run   # 在 src-tauri 下（没有开关了，镜子就是唯一的路）
```

实机验证要点（**尚未由人手做过**）：

1. 拖一个**文件**到资源管理器 → 进度条应当是流式的，落到目的地的字节与对端一致；
2. 拖一个**目录**到资源管理器 → 应当秒起拖，子树边复制边出现；
3. 拖到微信/QQ（只认 `CF_HDROP` 的应用）→ 应当能收到；
4. 抓起后**不落下**（拖回原处/按 Esc）→ 镜像里应当**什么都没下**（对比旧路：已经下完并留 6 小时）；
5. 观察日志里 `镜像项被打开/已关闭` 那两行带 `process=` 的字段：如果有个进程在没有任何人拖放的
   时候反复读镜像（索引器/杀软），会在这里现形 —— 那是白下载的来源。

## 6. 还没验证的部分（别当成已完成）

- **OLE 拖放手势本身**：`DoDragDrop` 与目标应用的交互（跨进程复制、进度、失败报错）没有由人手
  拖过一次。集成测试覆盖的是"平台回调我们"这一半，拖放手势那一半只有代码审查。
- **移动语义**：目标应用若把拖入的文件**移动**（而非复制）进自己的目录，等于把占位符搬出同步根
  —— 落点可能是只有我们运行时才能读的文件。我们只声明 `COPY`，规范的目标会照做，但违规目标拦
  不住。微信/QQ 属于哪一类属于待测。
- **多目录并发**下 provider 线程池与对端请求的吞吐（每个目录一次 `/tree` + 一次回调）。
- `STREAMING_ALLOWED`（准许平台不落盘）没试过 —— 那是把镜像磁盘占用降到 0 的唯一开关，但它的
  语义是"准许"而不是"强制"，要实测确认。
- 卸载路径：镜像的注销挂在进程退出（`RunEvent::Exit`）；被强杀时注册会留下（实测确认会留下，
  下次启动靠 `is_registered` 自愈，见 3.7）。真正的卸载器还需要"删镜像树 + 注销"这一步。

## 7. 旧路与开关的下场（已执行）

实机场景（776 MB 单文件、目录、微信/QQ）与"抓起不落下"都验过之后，旧的两条路与验证期开关
**已整体删除**：

- `staging_*`（`staging_eligible` / `staging_dir` / `stage_peer_item` / `download_peer_file` /
  `sweep_staging` / `STAGE_MAX_*` / `STAGE_TTL`）；
- `Payload::Virtual` / `VirtualItem` / `walk_peer_item` / `single_file_item` / `group_descriptor` /
  `PeerStream`（自定义 `IStream`）以及 `CFSTR_FILEDESCRIPTOR`/`CFSTR_FILECONTENTS` 两个注册格式；
- `ORBDROP_DRAG_MIRROR` 开关（`mirror::enabled()`）。

结果是 `drag.rs` 从 1753 行降到 ~930 行，OLE 数据对象只提供 `CF_HDROP` + `Preferred DropEffect`；
对端项的准备就是一句 `mirror::place`。原来的 `tests/drag_virtual.rs`（专测那两条路）删除，
其中仍然成立的两条判据搬到了 `tests/peer_metadata.rs`（老版本对端的 `/stat` 回退）与
`tests/mirror_hydrate.rs`（界面的过时 `is_dir` 以元数据为准）——**后者当场抓到一个真 bug**
（见 3.2 附近的 `place_item`：校正过的判断没被用于建占位符，文件被说成目录时会建出目录占位符）。
