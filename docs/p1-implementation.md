# OrbDrop P1 实现指南

> ⚠️ **后续改动（拖放镜像那一批）**：本文 §「拖拽下载」里写的"小项提前转存到 `staging` / 大项走 OLE 虚拟文件"**已经不是现在的实现** —— 那两条路连同验证开关已整体删除，对端项统一走 CFAPI 镜像（本地占位符 + 按需拉字节，`src/mirror/`）。本节余下的结论里仍然成立的是：`/shares` 的 `isDir` 必须报真元数据、`/file` 的空 `path` 要走"共享项根自身"、跨进程拖放只有 OLE 一条路。详见 `docs/cfapi-mirror.md`。

**设备状态模型**（贯穿 P1 所有模块）：

```
未绑定 ──配对──▶ 已配对 ──点击"连接"／启动恢复──▶ 长连接
 │                │                                   │
 │                │──点击"断开"（断链 + 本机暂停，两者都跨重启）─┤
 │                │    └──任一端点"连接"──────────────▶ 长连接
 │                └──解除配对──────────▶ 未绑定（仍在线则留在列表，离线则不再列出）
 └──可推送（HTTP 直达，接收需同意）
```

- **未绑定**：mDNS 发现/手动添加，无 token。可**推送**（HTTP 邀请直达，无需 WS/配对）
- **已配对**：token 交换完成。可推送；长连接**不自动建立** —— 设备行给「连接」按钮，由用户点
  （唯一例外：上次关机时它是长连接 → 启动恢复自动拨回来，见 F-16 与 §13 Step 2）
- **长连接**：已配对 + WS 实时连接（**用户点「连接」或启动恢复才建立**；mDNS 发现/探活都不拨号）。拖入文件自动广播给所有长连接设备

> 推送**不依赖**配对或长连接——邀请是普通 HTTP 请求，对端在线即可收到；接收方同意后才开始传输，同意制兜底安全。

## 5. 发现流程

### mDNS 注册（启动时，axum 就绪后）

```rust
// discover/mod.rs
pub async fn register_mdns(port: u16, name: &str) -> Result<MdnsResponder> {
    let mdns = Mdns::new()?;
    let hostname = hostname();
    let service_info = ServiceInfo::new(
        "_orbdrop._tcp.local",
        name,              // 设备显示名
        &format!("{}.local.", hostname),
        "",                // host target
        port,
        &["name=".to_string() + name,
          "ver=1"],
    )?;
    mdns.register(service_info)?;
    // 注册后的 service_info 会自动广播
    Ok(mdns)
}
```

### mDNS 扫描（后台任务）

```rust
// 监听 _orbdrop._tcp 事件
pub async fn scan_mdns(tx: mpsc::Sender<PeerEvent>) -> Result<()> {
    let mdns = Mdns::new()?;
    let receiver = mdns.browse("_orbdrop._tcp.local")?;
    loop {
        if let Ok(event) = receiver.recv_async().await {
            match event {
                MdnsEvent::ServiceFound(info, ..) => {
                    let peer = PeerDevice::from(info);
                    // 检查是否已配对（凭据文件里有向设备 token）
                    peer.is_paired = credential::has_peer(&peer.id);
                    tx.send(PeerEvent::Online(peer)).await;
                }
                MdnsEvent::ServiceRemoved(info, ..) => {
                    tx.send(PeerEvent::Offline(info.get_hostname())).await;
                }
            }
        }
    }
}
```

### 在线状态判定（F-13）

mDNS 只在对方主动告别或记录过期（约 2 分钟）时报告离开，且同名实例重启后浏览器未必重新解析，
所以在线状态由三条信号共同决定：

| 信号 | 触发 | 语义 |
|---|---|---|
| mDNS `ServiceResolved` | 对方注册/更新 | 立即标在线（并补全 ip/port），并收拾同一地址上的旧身份（见下） |
| WS 长连接建立/断开 | 已配对设备 | 权威信号：连上即在线；断开时**只在没有可拨地址时**才标离线（见"没有地址的对端"） |
| `/pair/info` 探测（每 5s，1.5s 超时） | 上面两条之外的兜底 | **回话里的 id 是这台设备**才算在线；地址上换了别的 id 则按"旧身份"处置 |
| `/discover`（同一趟 5s 循环，**只在手里有该对端的 token 时**替代上一条；**长连接活着的那几台也照走这一问** —— 链路只证明"跟这一台的关系"，不证明"它的视野已经同步过"） | 已配对设备 | 除了身份，还带回「对端此刻看得见的设备」**整份视野**（F-11a 跨网段发现：多网卡时每一段都在里面，别台设备转述来的不在）。对端 401/404 时退回 `/pair/info`；连不上则直接判离线，不再打第二遍 |

前端只渲染 `online` 设备，因此在对方退出后数秒内该行从列表消失；地址簿与凭据保留，
对方再上线会自动重新出现（不产生重复行）。

**对端报好几个地址时挑哪一个当拨号目标**（`discover::pick_address`）：mDNS 的地址记录是
**一块网卡一条**，对端的有线/无线/热点/VPN/WSL 各有各的地址，而对端这一侧把它们合成一个
`HashSet` —— 随手 `next()` 就是随机挑一块网卡，对端一插网线/开热点/换 Wi-Fi，设备行就可能
指向一个到不了的地址（看着像"地址变了不刷新"，其实是挑错了那一条）。排序：**与本机某块网卡
同网段**（本机直接能到；对端换网段后这一档跟着换，不必等它旧地址记录的 TTL 120s 过期）→
其它私网 → 其它全局 → 链路本地 `169.254`；同级按地址升序（集合不变则结果不变，地址不会
自己跳）。回环不算"本机网卡上的地址"（模拟器会把本机回环拍过来）。

> mDNS 的**广播**那一半不用本机管：注册时 `enable_addr_auto()`，mdns-sd 的 daemon 自己每 5s
> 查一次网卡列表（`check_ip_changes`），新网卡当场把服务播上去、消失的网卡把地址撤掉。
> 撤掉的那一条**不发告别包**（crate 只改本地记录），所以对端缓存里的旧地址要等 A 记录
> TTL（120s）自然过期才消失 —— 同一网段内 DHCP 换号时，最多会有约 2 分钟挑到那个死地址的
> 窗口（上面那套排序管不了"两个地址都在本机网段里"的情形）。

**没有可拨地址的对端（安卓模拟器 / NAT 后面的设备）**：来源地址是 TCP 给的、对端自报的端口
也是它给的，但**这一对不一定能拨回去** —— 模拟器把宿主回环别名（`10.0.2.2`）拍成宿主的
`127.0.0.1`，本机这一侧看到的来源地址于是**本机自己**。判据是
`net::observed_dial_target(source, reported_port, 本机监听端口)`：地址在本机网卡上（含回环）
且端口正好是本机在听的那个 → 那一对**一处都不记**（`("", 0)`）。少了这一步会一路错下去：
探活问回自己、把**本机的**证书指纹钉到对端名下、最后这一行被当成"这个地址上换了设备"
作废 —— 而它此后再没有地址可问，设备行就永远停在「离线」，尽管对方的长连接一直好好地在
（用户报的就是这个现象）。判据必须带上端口：同机多开（`ORBDROP_ALLOW_MULTI`）时
`127.0.0.1:<另一个端口>` 是**合法**的对端地址。

这条判据是共用的，凡"把 TCP 来源地址当成对端地址记下来"的地方都要过它：配对码那条路、
配对邀请那条路、`/chat` 入站登记（设备行）、以及推送邀请里的回执地址 —— 共四处，全部走
`net::observed_dial_target`。

这种对端（地址为空、端口为 0）**探活问不到、mDNS 也帮不上**：地址要么没有，要么是模拟器那张
**从本机拨不通**的脸（guest 的 `10.0.2.15` —— NAT 只允许 guest→host 方向的发起；宿主这一侧连
它等于连一个不存在的地址）。可达性于是只剩一条证据：它自己拨进来的那条长连接 ——
建立即在线（「长连接」）、断开即离线（消息排队等它下次拨进来时 `flush_queued` 送出去，
见 `ws::session::run_inbound_session` 收尾那段）。配对落库（`pair::commit_pairing`）也按
"有没有地址"给 `online`：没有地址就先记离线，不许先挂一颗绿点。

**指纹只认"确实是这台设备"的那一次**：探活的 `/pair/info` 回了 200 但 id 对不上（地址上换了
设备）时**不钉指纹**，否则会把别台设备（上面那一路里就是本机自己）的证书记到这一行名下，
下一次真去连它就成了"指纹与钉住的不一致"。


**设备 id 必须稳定**：`deviceId` 是地址簿与凭据的键。配置里所有其他字段都带 serde 默认值，
缺字段（旧版本配置/手工裁剪）只补默认值，绝不整份重置 —— 否则每次启动都会换一个 id，
对端就会为"同一台设备"多出一行，并让旧行上的配对码失效。

**设备 id 变了怎么办（去重的正题）**：id 是**唯一**的去重键 —— 不看名字、不看 ip（同名不同机、
同机多实例都真实存在）。用户清一次数据目录（`config.toml` 没了）就会换一个 id，而对端
手里那行还指着同一个 ip:port。两条规则收口：

- 探活与 mDNS 发现都必须核对**身份**：`/pair/info` 回的 id 不等于这一行记的 id，就说明
  这个地址上已经不是它了。只按"有人答话"判在线的话，旧行会永远在线 —— 列表里于是
  出现"两个同名设备，一个已绑定、一个未绑定"，且旧行永不消失。
- 核对之后按 `/pair/info` 的另一半回话（`pairedAs`：对端把本机带过去的 token 认作谁）分两路：
  - 认得出（= `pairedAs` 是本机 id）→ 对端只清了**配置**（device id 换了）而配对凭据还在：
    这一行**迁到新 id**，凭据的键一起换（`credential::rekey_peer`，token 值不变），配对状态与
    "长连接"记忆都跟着走，列表里只剩一行。
    （凭据文件与 `config.toml` 同在数据目录：只删/丢掉配置文件时凭据还在，正是这条路；
    整个数据目录一起清掉则是彻底重置，两端都得重新配对。）
  - 认不出 → 关系真断了：旧行只作废地址、标离线（**不动**凭据与配对记录，对端拿原 id
    回来还能用），列表里剩下的是 mDNS 发现的新身份。

### 本机隐身（F-94）：`Config::online` + `presence_middleware`

上面这一整套判的是**对端**在线。本机自己也有一档状态（面板右上角状态框，`Config::online`，
落盘跨重启），值为 `false` 时本机**主动退出局域网**：

| 动作 | 位置 | 为什么必须一起做 |
|---|---|---|
| 注销 mDNS 广播 | `discover::service_fullname` + `ServiceDaemon::unregister` | 按**服务全名**精确注销会发一条 TTL=0 的告别包；只丢掉 daemon 的话，对端缓存里的记录要等 TTL（约 2 分钟）才消失 |
| 断开全部长连接与拨号循环 | `WsManager::drop_all` | 会话与拨号任务是"参与网络"的两条腿；暂停标记（`paused`）**不动**，那是每台设备的人为意图 |
| 一切入站请求回 503 | `server::presence_middleware`（整张路由的最外层） | 对端每 5s 打一次 `/pair/info` 探活，只要还应答它就判本机在线 —— 只注销 mDNS 瞒得住发现、瞒不住状态。WS 升级也在公开路由上，必须在升级之前被拦下 |
| 现有设备行标记离线 | `lib.rs::set_online` | 离线期间连接/推送都会被拒，列表里留着绿色的「在线」pill 只会骗人；切回在线后 5s 探活会纠正 |

服务器**不停**：切回在线要立刻可用，而"503"与"连不上"对调用方是两种不同信号。
切回在线 = 重新注册 mDNS + `restore_links_on_startup`（按地址簿里的长连接记忆接回来）。
对外动作（`connect_peer` / `push_paths` / `pair_start` / `pair_confirm` / `pair_invite`）在离线时
由 `ensure_online` 直接返回错误：这些动作都要对端能回连本机，放出去只会卡到超时。

## 6. 配对流程（F-12）

### 状态机

```
        A 端（发起，显示码）                 B 端（输入码）
    ┌────────────────────┐            ┌────────────────────┐
    │ 点击设备行「配对」    │            │ 点击「配对」打开弹窗 │
    │ pair_start          │            │ 在「输入对方设备上显示 │
    │ 本机生成 6 位码      │            │ 的配对码」里填码      │
    │ 存内存 2 分钟        │            └─────────┬──────────┘
    │ 弹窗显示码 "482916"  │                      │
    └─────────┬──────────┘                      │
              │ 用户读一眼 A 屏幕上的码             │
              │        POST /pair                 │
              │  { peerId, peerName, code }        │
              │◄───────────────────────────────────┘
              │  验证码一致？(单次有效，2 分钟过期)
              │  生成 token → 存凭据文件（键 = B.id）
              │  标记 B 已配对（保留已知 IP:port）
              │  A.id < B.id → 拉起 WS 长连接
              │  返回 { token, peerId, peerName }
              │ ─────────────────────────────────►  B 存同一枚 token
              │                                    标记 A 已配对
              │                                    B.id < A.id → 拉起长连接
              │                                    弹窗自动关闭 + 提示配对成功
              │  A 收到 pair://completed → 弹窗关闭 + 提示
```

任一端都能发起：谁点了「配对」谁显示码，另一端在同一个弹窗里输入即可。
未绑定设备可用弹窗里的「添加设备」（IP / IP:端口，探测对端 `GET /pair/info`）先入库（F-11）。

### 配对邀请（免输码那条路，同一个弹窗里的「发起邀请」）

```
        A 端（点「发起邀请」）                B 端（在通知里点「接收/拒绝」）
    ┌────────────────────┐            ┌──────────────────────────────┐
    │ 弹窗里点「发起邀请」  │            │ 面板右下角挂一条通知：         │
    │ pair_invite(peerId) │            │ 「「A」请求与你配对」+接收/拒绝 │
    │ 记一条外发邀请       │            └──────────────┬───────────────┘
    └─────────┬──────────┘                          │
              │  POST /pair/invite                  │ 用户点「接收」
              │  { inviteId, peerId, peerName, port}│
              │────────────────────────────────────►│ 铸 token → 存凭据（键 = A.id）
              │  （请求一直挂着，等 B 的用户做决定）   │ 标记 A 已配对（IP = TCP 来源，端口 = A 自报）
              │                                     │ emit pair://completed / devices://changed
              │  ◄──────────── 200 { token, peerId, peerName }
              │  存同一枚 token（键 = B.id）+ 标记 B 已配对
              │  emit pair://completed → 弹窗收起 + 通知组那张卡收掉 + 提示配对成功
              │
              │  被拒绝 / 60s 没人处理 / A 点「取消」→ 403（正文即原因）
              │  → emit pair://invite_failed → 通知组那张卡收掉并写明原因
```

- **推送靠点击**：A 点一下按钮，后端就地发一次 `POST /pair/invite`（不需要 WS，也不需要预先配对）。
- **本机不等在弹窗里**：点完「发起邀请」弹窗当场收起，这条邀请落成面板右下角通知组里的一张
  「等待对方确认配对」卡（与"等待对方同意"的推送卡同一位置、带「取消」）—— 对方处理得慢也不占着弹窗。
  同一台设备再发一次会先把上一条还挂着的邀请撤回来，不让对面堆两条一样的。
- **同意制**：B 不点「接收」就不会交换 token；60s 没人处理，两边同时作废（B 的通知消失、
  A 那条挂着的请求以 403 收场）。
- **撤回是双向的**：A 点「取消邀请」→ `POST /pair/invite/withdraw` → B 界面上那条通知跟着撤掉
  （不然对面点「接收」才发现"邀请已作废"）。
- **冒充已配对设备必须出示 token**：自称的 `peerId` 在本机是**已配对**的，就要带上能反解成它的
  Bearer token（`deliver_invite_http` 会自动带）—— 与 `/push/invite` 同一道关。没有这道关，
  谁都能自称你的老搭档，用户点一次「接收」那台设备的 token 就被换成了对面手里的那枚。
- **先伸手后落库**：接收方在 oneshot 送得到（= 发起方还在等）之后才写凭据与地址簿
  （`pair::accept_invite`）；发起方拿到 token 就落库，不因为"用户中途点过取消"丢弃
  （对端那边已经记下了，丢掉只会让两边不一致）。
- 两条路的落库收敛到同一个入口 `pair::commit_pairing`（写凭据 + 写地址簿 + 预写 BC profile + 广播事件）。

### 代码结构

```rust
// pair.rs —— 待验证码，键 = 对端 device id（每个对端只保留最近一枚码）
struct PairStore { pending: Mutex<Vec<(String, PendingPair)>> }
struct PendingPair { code: String, created_at: Instant }
const CODE_TTL: Duration = Duration::from_secs(120);   // create_code / verify_code

// POST /pair 请求体（camelCase）
struct PairRequest {
    peer_id: Option<String>,   // 输入码一方自己的 device id
    peer_name: Option<String>,
    code: String,              // 发起方屏幕上显示的那 6 位码
}

// POST /pair 响应（camelCase）—— 邀请那条路的响应**完全一样**
struct PairResponse {
    token: String,
    peer_id: String,           // 验证方自己的 id（caller 以它登记对端）
    peer_name: String,
}

// 邀请（同一个 PairStore 里另两张表）
struct PairStore {
    invites: Mutex<Vec<PendingInvite>>,        // 进来、等本机用户决定的
    outbound: Mutex<HashMap<String, String>>,  // 发出、等对端决定的（取消时凭它找到对端）
}
struct PendingInvite { invite_id: String, peer: PairedPeer, responder: Option<oneshot::Sender<..>> }
const INVITE_TTL: Duration = Duration::from_secs(60);   // 与推送邀请同一个数
```

### 配对码生成

```rust
fn generate_code() -> String {
    let code: u32 = rand::thread_rng().gen_range(100_000..1_000_000);
    code.to_string()
}
// 6 位纯数字，100 万组合，2 分钟有效、单次使用
```

两条刻意的设计（都来自实际踩坑）：

- **码不绑定 peer id**：凭据就是屏幕上那串数字。绑定 + 对端 id 漂移（配置被重置、地址簿残留
  旧行、点错重复行）会直接报「配对码错误或已过期」，排查成本极高。
- **倒计时结束不自动换码**：前端只显示剩余秒数，过期后由用户点「刷新配对码」。
  曾按"过期自动刷新"每 2 分钟换码，对方照着屏幕输入时被静默换掉 → 报「配对码错误或已过期」。

### token 交换

配对成功时（token 由**验证方**生成，双方保存同一枚）—— 邀请那条路里"验证方"就是**收下邀请的一方**
（它点「接收」时铸一枚放在那条挂着的 HTTP 请求的响应里还给发起方）：
- A 生成 token（32 字节随机，hex 编码）
- `credential::set_peer(&B.id, &token)` → A 的凭据文件
- 响应返回 token → B 收到 → `credential::set_peer(&A.id, &token)` → B 的凭据文件
- 两端各自 `mark_paired`；长连接**不在这里建** —— 用户点「连接」时才拨号（`ws::ensure_link_now`），
  或是下次启动时按上次的记忆恢复（`ws::restore_links_on_startup`）
- 后续所有 HTTP 请求 `Authorization: Bearer <token>` / WebDAV `Basic base64("OrbDrop:<token>")`（用户名不参与校验，只作发起方标记；服务端取第一个冒号之后的部分当 token）

### 凭据文件（`%LOCALAPPDATA%\OrbDrop\credentials.dat`）

全部已配对设备的 token 是**一份映射、一个文件**（P0 起它曾放在系统凭据库的单条凭据里；
那次搬家是为了绕开 Windows 单条凭据 **2560 字节上限**——按真实尺寸约 11 台设备就写不进去、
配对会直接 500——顺便让"一键清空"变成一个删除动作，而不是平台相关的枚举代码）。

> ⚠️ **本节后续已被取代（传输加密那一批）**：映射里现在每条还带**对端证书指纹**
> （格式 v3，见 `credential.rs`），本机另有一份 `identity.pem`（自签证书 + 私钥，
> 只生成一次）。**系统凭据库那条路已经彻底删掉**——不再有只读回落、不再有
> `migrate_legacy` / `migrate_legacy_entry`、`keyring` 依赖也去掉了；下面提到它们的地方
> 只当历史看。就地改写仍然只在启动时发生一次，它现在会把 v1/v2 一起升到 v3。

```text
<一整块 base64：每 76 字符换行，没有空行、没有版本头、没有署名>
```

内层明文（**混淆前**的那份内容，文件里看不到）才是真正的结构：

```text
ODBF 2                                   ← 魔数 + 十进制版本（版本按文本读，不按宽度）
{"<device_id>":"<token>",…}              ← 裸 JSON
# 177plus                               ← 尾署名，`#` 开头的行都是注释
```

- **这是遮挡，不是加密**：文件 = 内层明文按固定密钥（`credential::SCRAMBLE_KEY`，就写在源码里）
  逐字节异或、再 base64、每 76 字符换行。于是打开文件看不到版本头、看不到署名，也不是
  "标准 base64 一解就是 JSON"（解出来是异或后的字节）。**但仅此而已**：密钥在源码里、算法是
  异或，任何人拿到文件都能解回明文 —— 别把它当保护，也别在它上面继续叠"更复杂的"假加密
  （零保护，却会让后来的人以为它有保护）。真正要加密只能引入密钥保管
  （Windows DPAPI / macOS Keychain），本版不引。
- **老格式（v1）只读兼容**：`ODBF <版本>` 头 + base64 正文 + `# 177plus` 署名 = `FORMAT_VERSION 1`。
  启动时（`migrate_legacy_entry` 之后）调一次 `credential::upgrade_vault_format()` 就地改写成 v2；
  改不动只 warn（读兼容一直在，下次启动重来）。**写一律 v2** —— 于是升级是单向的：用回旧版本会
  读不到（旧版只认 v1 形状，会报"缺少格式头"）。版本闸门两种格式共用，比 `FORMAT_VERSION` 新的
  格式明确拒绝（"请升级 OrbDrop"），不瞎猜。
- **老数据自动迁移**：启动时（`run()` 里、`AppState::new` 之前）调一次
  `credential::migrate_legacy_entry()`，把系统凭据库里那条读出来写进文件，**写成功之后**才删那条
  （先删后写、中间崩一次就永久丢配对）。迁移是**单向**的：用回旧版本会读不到（旧版只认凭据库）。
- **读路径不改任何东西**：文件不在时只**只读**地回落到老条目。曾经把迁移挂在"读一次凭据"上，
  结果跑一次 `cargo test` 就把开发机真实的配对搬走并删掉了老条目 —— 读一个字节都不该改用户的东西。
- 单测（lib 内）一律走临时 vault 文件；集成测试靠 `ORBDROP_DATA_DIR` 指到临时目录
  （`config::data_dir` 的唯一出口，顺带给便携部署用）。

**凭据模块的两条硬规矩**（都是踩过才写下的）：

1. **读也要和写串行**。整份映射是**一个**文件，所有写都是"读-改-写"；不加锁地读会在别人
   改写的当口读到半截（原子写让"半截"变成"读到旧版本"，但读-改-写丢更新的问题还在）——
   表现为"刚配对成功的 token 查不到"（`has_peer` 突然说没有这台设备）。
   `credential::load_peers` 与写路径共用 `STORE_LOCK`（写路径内部用不取锁的
   `read_map_unlocked`，避免 parking_lot 互斥锁不可重入）。
2. **"读不到" ≠ "没有"**。凭据存储的瞬时故障（文件被占、同机多实例并发）不是语义事实：
   - 拨号循环里读失败只算"这次尝试失败"（退避重试），**不能**当成"没 token"退出 ——
     那会让重启恢复永久停在这个设备上，且不报错；
   - 探活/身份核对里读失败**什么都不做**（跳过这一轮）：带着错的前提去问，会得到
     一个"它不认我们"的假结论，进而把一条有效的行当垃圾处置（作废地址）。
   同理，凭据文件解析失败（被截断、被别的工具改过）**必须报错**，不能当成空映射 ——
   那会让下一次写回把别人的 token 抹掉。

## 7. 推送流程（F-50~F-54）

### 通知通道

| 目标设备状态 | 邀请方式 | 认证 | 接收侧要不要问同意 |
|---|---|---|---|
| **长连接** | WS 推送 `push_invite` 事件 | 链路本身就是 token 换来的 | **不问** —— 已绑定（已配对）设备直接收下 |
| **已配对（未长连接）** | HTTP POST `/push/invite` 直达 | Bearer token | **不问** —— 同上（配对即互信），落盘恒为 `下载目录/<发送方名>/` |
| **未绑定** | HTTP POST `/push/invite` 直达 | **无需认证**——同意制兜底 | **要问** —— 挂卡片等点「接收/拒绝」，60s 自动拒绝。用户点「接收」时若设了「每次询问」（S-02），先弹目录选择框定这次的**落盘根**（打开即下载目录），框里取消 = 拒绝这次接收 |

> 未绑定设备推送：邀请本身不认证（任何人都能发邀请，你同意才会传）；`GET /push/download`
> 摊销在**邀请 id** 上 —— 那是一枚只在这条邀请里出现过的 v4 uuid，对端刚凭它同意，
> 局域网明文 HTTP 里再套一层 token 换不到什么，需求本来就把安全性放在"接收方同意"这一步上。
> 已配对的推送仍然必须带 token（`routes_push::authorize`），否则等于谁都能冒充你的老搭档。

> `/push/invite`、`/push/report`、`/push/download` 三条都在**公开**路由面上（不带 auth 中间件），
> 认人规则写在各自的 handler 里；它们仍挂在 CORS 之外的那套 REST 命名空间里，与 WebDAV 面互不影响。

### 状态机

```
A（发送方）                                    B（接收方）
┌──────────────────┐                        ┌─────────────────────────┐
│ 选文件/文件夹      │                        │                         │
│ 发邀请：           │                        │        受邀             │
│  • 长连接: WS push_invite                 │                         │
│  • 其他:  POST /push/invite ─── HTTP ───► │ 面板右下角一条通知气泡     │
│  状态: invited（界面：等待对方同意）         │ 悬浮球左上角数字 +1       │
│                                           │                         │
│ ────────── 同意 / 拒绝 ──────────────── │ 点「接收」/「拒绝」        │
│   长连接: WS push_response                 │ 60s 没动作 → 自动拒绝     │
│   其他:   invite 请求的**同步响应**         │                         │
│  状态: accepted                            │                         │
│                                           │                         │
│      GET /push/download?id=&path=&offset=  ◄──── HTTP（B 主动拉取）   │
│      （offset 续传；取消时流就地断掉）        │ 流式写入 下载目录/        │
│ ◄───── POST /push/report（进度/完成/失败）── │ 发送方名/…（清单里的路径） │
│  状态: completed                           │                         │
└──────────────────┘                        └─────────────────────────┘
```

> **已绑定（已配对）设备不弹同意**：邀请一到就直接放行（`transfer::accept_invite`），界面上是
> 一条"正在接收"的通知；那条带「接收/拒绝」的气泡只留给**未绑定**设备。两条通道（WS / HTTP）
> 都是这个规则，两处各有一段代码：`ws::session` 的 `push_invite` 分支、`routes_push::push_invite_handler`。
> 依据是 token 就是那份信任：对已绑定设备来说，下面那段"受邀 → 同意"是**自动填上 `true`** 的。
> 认人这一步仍然不能省 —— HTTP 那条路上，自称已配对的对端必须出示能反解成它的 token。

> **两条通道说同一套协议**：HTTP 那两条路的请求体就是 WS 上的 `push_progress` / `push_done`
> 事件（同一个 `WsEvent` 序列化），发送方用同一个 dispatcher（`ws::session::handle_inbound`）
> 处理。邀请体比 WS 版本多一个 `port`：请求的**源端口**是一次性的，回执要发回发送方真正的
> 服务端口，所以它自报端口，ip 则取自 TCP 来源（不可伪造）。

### 回执丢了怎么办：对账（`PushAsk` / `PushState`）

上面那几条回执（`push_progress` / `push_done` / `push_response`）都是**一次、尽力而为**：
`report_to_sender` 原先只看"有没有长连接"，而 `ws::send` 只保证"塞进了当前会话的 mpsc 队列"——
"检查时链路还在、发的瞬间断了"这一档会**静默丢回执**。丢了之后的后果不是"等一等就好"：

- 发送方那一台一直停在 `invited`（卡片「等待开始（对方自动接收）」/ 会话气泡「等待同意」），
  到 `WS_INVITE_TTL = 300s` 被 `schedule_ws_invite_timeout` 落成 `failed`「对方未响应（5 分钟超时）」；
  而**对面其实早就收完了**（数据是接收方自己拉的，根本不依赖回执）。
- 也就是"对端已收到、本机写着失败"，而且以前**不会回正**（终态只落一次）。

现在是三层兜底：

| 层 | 做法 |
|---|---|
| 回执补强（接收侧） | `push_job::report_to_sender`：WS 队列**写不进去**（不只是"没有会话"）就退回 HTTP 回调；HTTP 那一跳按 0/1/3 秒退避**重试三次** |
| 对账（发送侧主动问） | 链路在就按时机问：**对端长连接刚建立**（`ws::session::run_inbound_session`）、**探活的每一拍发现链路在**（`state` 里两个 `chat::flush_queued` 调用点旁边）。内容 = 本机还没落终态的邀请号（`waiting_invites_of`），一次一批，只走长连接；同一台设备 20 秒最多问一次（`PushStore::ask_due`），回执丢了靠下一拍补上 |
| 终态分级（发送侧落账） | `push_job::late_success`：本机**猜的**失败可被对端更权威的终态改写 —— `Failed → Done`（收完了）/ `Failed → Rejected`（它明确拒绝）**允许**；`Cancelled` / `Rejected` / `Done` 作为**起点**时不许被改写（当事人明确表达过的意图）。批次走完不再立刻丢，留 `SETTLED_GRACE = 600s`（`settle_batch` / `sweep_settled_batches`，由 `lib.rs` 里一分钟一拍的清扫任务收尾）—— 宽限期内的答案才落得下来 |

对账的答案由接收方按**自己的记录**给出（`PushStore::answer_invite_state`）：

| 答案 | 含义 | 发送方落成 |
|---|---|---|
| `done` | 收完了 | `done`（含纠正本机推测的失败） |
| `failed` / `cancelled` / `rejected` | 处理过、没成 | 对应终态 + 原因 |
| `waiting` | 本机还拿着这条邀请（等用户处理，或下载循环正在跑） | 已配对 → `sending`（它自己就开收了）；未绑定 → 保持「等待对方同意」，别改口 |
| `unknown` | 本机**没见过**这条邀请 = 那条邀请根本没送到 | 当场 `failed`「对端没有这条邀请（没送达）」，不必再等满 5 分钟 |

两条纪律：记录来源只有 `inbound`（在手里）+ `PushStore::recent`（处理完的结局，有界 64 条，键按
**发送方**校验 —— 别人的会话问同一个 id 一律 `unknown`，见 `answer_refuses_ids_from_another_sender`）；
两条通道（WS / HTTP）说的仍是同一个 `WsEvent`，落账也走同一个 `batch_set`。

> **已知取舍**：宽限期内发生的纠正会把已经收起的卡片重新推给界面（`push://batch` 是全量快照，
> 语义如此）。桌面前端因为 `settledBatches` 记过它，不会再弹 toast、也不会自动收起 —— 用户点
> 「知道了」即可。换来的是一句真话：那条推送其实是成功的。
>
> 与新版本混用是安全的：老接收方不认识 `push_ask` 会当未知事件忽略，发送方退回到"报告重试 +
> 5 分钟超时"的老行为，不会更差。

### 取消与拒绝

| 动作 | 结果 |
|---|---|
| 接收方点「拒绝」 | HTTP 邀请的同步响应 +（有长连接时）WS `push_response` + 本机那条通知撤掉 |
| 接收方点「取消接收」 | 邀请从内存移除 → 下载循环收手 → 回执 `push_done{failed, 接收方已取消}`（发送方的进度卡跟着收掉） |
| 发送方点「取消」 | 主动告诉对端（长连接 WS / 否则 `POST /push/report`）：**邀请还挂着**就把对面那条邀请通知撤掉；**正在传**则由下载端点当场断流、下一次请求拿 410，两边几百毫秒内一起收手 |
| 发送方点某台的 ✕（一批多台） | 等同"对那一台点取消"：只撤它那条邀请，其余几台照走；它那一行落成「已取消」（终态只落一次 —— 对端随后补报的失败不会把它改写成「失败」） |
| 发送方点「取消全部」（一批多台） | 逐台走上面那条；单台的失败（对端已经不在网上之类）不挡住其余几台的取消。整批都取消后卡片立刻收掉 |
| 60s 没人处理（**只对未绑定设备**） | 自动拒绝（两条通道共用 `transfer::schedule_invite_timeout`），发送方的等待不会落空。已绑定设备的邀请一刻都不等人 —— 它压根不排这个超时 |

> **取消必须双向可见**：任一端点了取消，另一端那张卡片就不能再挂着 —— 界面收到的是同一条
> `push://done{status:"cancelled"}`（发送方自己的那张卡也由它收掉）。漏掉这一层的后果是
> 对面一直停在「等待对方同意 / 正在接收」，点下去才发现早就没了。

### 推送 job 模型

```rust
// transfer/mod.rs —— 源清单：从"用户选中的那批路径"直接生成，不再依赖共享项
struct PushSource {
    name: String,                      // 对端落盘子目录名（多选 = 共同父目录名或「N 项」）
    files: Vec<FileEntry>,             // 清单（相对路径 + 大小），对端看到的就是这一份
    sources: Vec<(String, PathBuf)>,   // 清单相对路径 → 本机绝对路径（只在本机用）
    total: u64, is_dir: bool,          // is_dir = 清单是否权威（单文件推送是唯一例外）
    count: usize,                      // 用户选了几项（>1 = 多选）
}

// transfer/push_job.rs
enum PushStatus { Invited, Accepted, Downloading { received, total }, Completed, Failed(String) }

struct PushJob {           // 发送方：**一台设备一条**（清单不在这里 —— 见下面的批次）
    id, batch_id, peer_id, peer_name, name, is_dir, sources,
    peer_paired: bool,     // 决定下载端点怎么认人
    status: PushStatus,
}

enum TargetState { Invited, Sending, Done, Cancelled, Rejected, Failed }

struct BatchTarget { peer_id, peer_name, invite_id, paired, state, received, error }
struct PushBatch {         // 发送方：**一次操作 = 一批 = 界面上一张卡片**
    id, name, count, per_target_total, targets: Vec<BatchTarget>, last_emit,
}
// 单台推送也是一批（targets 只有一条）—— 后端与界面只有一条路，不为"多设备"分叉出
// 第二套事件/收尾逻辑。批次活在"整批走完"之前（最后一台落终态时丢掉）。

struct InboundInvite {     // 接收方（**与单台推送完全一致**：它不知道批次的存在）
    invite_id, sender: PeerInfo, name, size, is_dir, count, files,
    callback: Option<(String, u16)>,        // 没有长连接时回执发这儿（"来源地址 + 自报端口"
                                            // 指的其实是本机自己时给 None，见 §5 那条）
    responder: Option<oneshot::Sender<bool>>, // HTTP 邀请的同步回执口
}
```

### 吞吐、进度与运行时（几个坑，别踩回去）

| 位置 | 事实 |
|---|---|
| 接收循环 | **不按块休眠**。P1 初版在每块之后 `sleep(50ms)` 当节流 —— 块只有几 KB，于是速度被按死在几十 KB/s，几十 MB 的文件要几分钟，发送方的进度条看起来"永远是 0%"。现在传输不限速，**限速只作用于进度事件**（`REPORT_INTERVAL` = 200ms，发送方回执与本机 UI 事件共用同一个节流点）。 |
| 下载端点 | 判"这条推送还在不在"用 `PushJob::cancel`（原子量，`remove_job` 置位）。用 `job()` 会把整份文件清单每块克隆一遍；用 `has_job()` 则是每帧抢一次全局互斥锁 —— 两者都别退回去。 |
| 流式帧大小 | `ReaderStream::new` 的默认容量是 **4KB**：1GB 文件 = 26 万次 `spawn_blocking` 派发 + 26 万条 4KB 的 TLS 记录。统一走 `net::STREAM_CHUNK`（256KB）。**这条同时作用于 `/file`（镜像水合那条路）**：只改分帧大小，不改"短读 = 到末尾"的语义。 |
| 每请求的固定开销 | `/push/download` 不再每请求 `canonicalize()`（清单生成时算一次，存的就是解析过的绝对路径）、不再每请求读凭据库（`credential::peer_tokens()` 是带版本失效的缓存，写路径 `write_vault` 一落盘就作废）、`sources` 是 `HashMap` 而不是列表（2 万文件 × 2 万请求 ≈ 2×10⁸ 次字符串比较）。 |
| 续传记录落盘 | `ResumeStore` 是"内存 + 250ms 节流 + 原子替换 + 紧凑 JSON"。**绝不能改回"每次 save 都整份重写"**：2 万文件的目录累计写入是 GB 级（O(n²)）。纪律：**记录里的 offset 只在字节 flush+sync 之后才写**（`save` 之前先 `flush`/`sync_data`）。 |
| 进度回执 | 节流后由 `report_to_sender` 发出：长连接走 WS，否则 `POST /push/report`（请求体就是同一个 `WsEvent`）。发送方的 job 状态由**这条路径**更新（与推给界面的 `push://progress` 同一处），所以"界面能看到进度"和"job 状态在变"是同一个事实。 |
| 后台任务怎么起 | **同步** Tauri 命令跑在主线程上，那里没有 Tokio reactor：`tokio::spawn` 会 panic（"点一下就闪退"），而"没有运行时就跳过"会把这次点击**无声吞掉**（推送接收踩过：点「同意」后下载任务被丢掉，两边永远停在 0%，日志里只有 `no tokio runtime here; task skipped`）。现在统一走 `task::spawn`：当前运行时 → 否则退回 Tauri 的全局运行时（`tauri::async_runtime`，随用随建），不再有"起不来"这个分支；命令能写 `async fn` 就写（`accept_push` / `cancel_push` / `cancel_receive` 都是）。 |

### 新数据面：分帧并发 + 块级续传（`POST /push/stream`）

老路子（`GET /push/download`，一次一个文件、串行）在"一个目录里几百上千个小文件"时慢得没有
道理：时间几乎全花在**每个文件的往返**上（RTT + 发送端每次的打开/元数据/认人），带宽反而
闲着。新数据面把这件事拆成"块任务"，一次请求带走一批：

```
POST /push/stream   { id, blockSize, tasks:[{path, index}] }

响应 = 分帧记录流：
  0x01 FILE   : path|size|mtime|blockSize|blockCount          ← 身份对账（源变了就判失败）
  0x02 BLOCK  : path|index|offset|len|payload[len]|sha256(32) ← 哈希**尾随在载荷后**
  0x03 SKIP   : path|reason   0x04 ERR: path|msg   0x05 SOURCE_CHANGED   0x00 END
```

| 主题 | 事实 |
|---|---|
| 谁选协议 | 邀请里的 `caps` 带 `stream1` 才走新路（`InboundInvite::supports_stream`）。老对端不带 → 老循环，滚动升级不需要同步。 |
| 谁定块大小 | **接收方**（设置里的「分块大小」，默认 4MB）。发送端只按 `index * blockSize` 算区间；接收端对回来的 `offset/len` 做**硬校验**（区间必须正好是它要的那一块）。 |
| 小文件 | `size ≤ 1MB` 的按批合并（≤256 条 / ≤8MB 一个请求），"一个文件的往返"摊到几百个文件上。 |
| 大文件 | 按块切成任务，多个 worker（设置里的「传输并发数」，默认 4）同时啃同一个文件的不同块 —— 每块各自开句柄 `seek` 到自己的 offset 写，互不重叠。 |
| 完整性 | 每块的 SHA-256 由发送端**边读边算**、接收端**边写边算**，读完比对：不符 → 这一块不置位、不记进度、重排一次，再不符 → 判这条文件失败。长度另有一道（`FILE` 的 size 必须等于清单里的 size）。 |
| 续传 | 键是**文件身份** `sha256(对端 id|路径|大小|mtime)[..16]`，位图按块记在 `resume.json`。因为键里**没有邀请 id**，"传失败再推一次"是接着传，不是从零开始。 |
| 落盘 | 一律先写 `<key>.orbdrop-part`，**长度核对 + fsync 之后原子改名**到最终路径：最终路径上只会是"不存在"或"校验过的完整文件"，永远不会有半截文件顶着真名。 |
| 记进度的前提 | 位图里的每一位都要求"这块的字节已经 flush + sync 落盘"（`write_block` 里先 `sync_data` 再 `complete_block`）。崩在中间只会丢"最后那几块还没记上的"，不会出现"记录说完成、内容是垃圾"。 |
| 失败隔离 | 单条文件失败（对端打不开/源变了/两次哈希不符）只记那一条，其余照跑；收尾按"有没有失败"回 `completed`/`failed`（原因里带条数与第一条）。连接级失败是另一回事：整批退避重试（1s/2s/4s）。 |
| 取消 | 接收端：邀请被取走（`cancel_receive`）→ reporter 置 `cancel`，worker 在一个块内收手；发送端：`PushJob::cancel`（`remove_job` 置位）→ `CancelAwareReader` 断流 → 接收端下一次请求拿到 410。 |
| 落盘确认（fsync） | **按大小分档**：`size ≥ 1MB` 才在改名前 `sync_all`，小文件不做。理由是实测的：每文件一次 fsync 在 NTFS 上要几毫秒，3000 个小文件就是十几秒（早期版本因此掉到 0.3 MB/s，比老循环还慢 4 倍 —— 见下面的实测）。小文件的字节本来就在页缓存里，进程被杀/崩溃不丢（内核还在），只有"断电/系统崩溃"那一档需要 fsync，而那正是所有不做 fsync 的拷贝工具（含 Windows 自己的 `CopyFile`）共同的暴露面。 |
| 收尾复核 | 改名之前只复核**接手来的**块（跨会话续传的那部分，位图里"以前就在盘上"的那些）：那是位图唯一有可能撒谎的地方（系统崩溃会丢页缓存）。本次会话现场收到的块在到达时就与对端的摘要比对过，再读一遍纯属重复劳动 —— 128MB 的文件实测会多花 2 秒（翻倍）。 |
| 速度（本机回环 TLS，热缓存） | 3000 个小文件（4KB）：老循环 **7.03s（2.34 ms/文件）** → 新协议 **1.72s（0.57 ms/文件）**，**4.1×**；单个 128MB 大文件 **1.33s → 101 MB/s**（千兆的理论上限是 118 MB/s，基本打满）；混合（1500 小 + 128MB）**2.50s / 55.6 MB/s**。小文件那一段的时间几乎全花在"建文件/改名/记账"上（12MB 的字节在链路上只要 0.12s），所以这是文件系统的地板，不是链路的。 |
| 与镜像（CFAPI）无关 | 镜像水合走 `/file` + `peer_fs`，新协议走 `/push/stream`，两者**不共用**并发闸门、不共用落盘根、不共用状态。共享的只有 TLS 配置与 token 反解（后者现在是带版本失效的缓存）。`/file` 那条路唯一受影响的改动是**分帧容量 4KB → 256KB**（不改字节总数、不改"短读 = 到末尾"）。 |

```

               购物车：底 [3] 报告.txt 等 2 项 ▲ ── 点开向上展开，逐项 ✕ 或「全部取消」
```

- **设备页不给推送**：行右侧那颗是「发消息」（打开与这台设备的会话，见 F-59），右键菜单里
  也没有「推送…」—— "推文件"是低频动作，挪进会话不再占位；设备页只剩连接/配对/解除配对这一套。

  所以"发给谁"由会话定、"发什么"仍交给同一个 `picker` 请求对象。
- **搜索框（F-58，纯前端）**：`DeviceTab` 的 `query` + `filtered` 只筛**显示** ——
  `devices` 一份不动（右键菜单与行内动作都按它查表）。
  匹配规则：**显示名**（F-101：设了备注就是「备注(设备名)」，所以备注也搜得到）或 `ip` 的子串
  （不分大小写）；空串/纯空白不过滤。计数在筛选时
  换成「匹配 x / 共 y 台」，零命中走专门空态（写明只匹配名称与 IP + 「清除搜索」），**不能**
  摆「还没有已配对设备」那张（会像是设备丢了）。它常驻在「局域网设备 ?」右侧，
  且 `DeviceTab` 随标签切换重建 → 查询天然不跨标签残留。
- **设备备注（F-101）**：写入只有一处 —— 后端 `set_device_remark(peerId, remark)`（空串/纯空白
  = 清除，超过 `config::REMARK_MAX_CHARS`（24 字）按**字符**截断并返回真正存下的值）。
  落盘在 `Config::device_remarks`（`设备 id → 备注`，`list_devices` 每条带一个 `remark`），
  **单独一张表、不塞进 `peers` 条目**：备注是本机的看法，不是那台设备的事实 ——
  解除配对（条目被打回"未绑定"）、重新配对（换 token）都不该把它抹掉。
  界面侧拼装也**只有一处**：`stores/devices` 的 `deviceDisplayName(d)`（`remark ? \`${remark}(${name})\` : name`），
  凡是给人看的设备名都走它（设备行、标签栏、会话标题、收件人选择框、推送卡、toast 与通知）；
  名字来自别处的场合（推送快照里的 `target`、邀请里的 `sender.name`）走 `peerDisplayName(id, fallback)`。
  右键菜单那一项**排在状态分档之前、不受任何条件影响**（离线行、未绑定行都能改 —— 纯本机动作），
  菜单里顺手写出现在那条备注（行内截断、全名在 `title`）。对话框里"当前设备名"与保存后的提示
  报的是**对端自己的设备名**、不是显示名（否则一句提示里两半都在说备注，看不出改的是哪台机器）。
  前后端 `maxlength` / `REMARK_MAX_CHARS` 是同一个 24，改一处就得改另一处。
- **工具条这一行的光学对齐（像素级实测出来的，别按感觉调）**：这一行是「中文 + 圆 + 输入框 +
  中英混排台数」。圆的盒子和输入框本来就在行中线上（12.0 / 12.0，24px 行高），可**墨迹**不一定：
  11px 的中文字在字体盒里天然偏上（雅黑的 `ascent+descent` 13px 盒子里那 10px 墨迹的中心在盒中心
  上方 0.7px，加上行盒又偏上 0.3px = 合计 1px），所以「局域网设备」与台数各要 `top: 1px`
  压回中线（只挪绘制、不改布局，整数像素在 dpr 1 下仍清晰）；圈里的「?」要 `line-height: 12px`
  （= 圈内空 14−2×1px，写成整数行盒，`align-items: center` 的居中量才是整数 0）+ `font-size: 11px`
  （墨迹正好 8px，上下各 3px）——原来的 9px + `line-height: 1` 留下 (12−9)/2 = 1.5px 的半像素，
  圈里的「?」因此差半像素。**输入框内部**（光标 15px、占位符墨迹 11px 在 22px 内空里）是
  **奇偶性**决定的 0.5px，改 line-height 没用（实测 12/14/16/19.2/22px 落点一模一样）：24px 盒高
  时文字类精确居中、光标 5/4 差半像素；25px 盒高则光标 5/5 精确、文字与圆又差半像素（实测）。
  选 24px（多数元素精确）并把这个事实写在这里，省得下次有人拿 25px 去换。
- **没有"先问文件还是文件夹"那一层**：系统选择框一次只能挑**一种**（Windows/macOS 的文件与
  文件夹是两种对话框；插件 Rust 侧也只有 `pick_file(s) / pick_folder(s)` 四个入口，**没有
  "文件或文件夹"混合模式**），而推送要的正是两者混选 —— 所以选择框自绘在面板里
  （`FilePicker.svelte` + `src-tauri/src/fs_browse.rs`）。自绘还顺带拿到原生框给不了的两件事：
  **选中的项跨目录累积**（原生框一换目录，之前选的就没）、顶部「常用」。
- 选择框由**一个"请求对象"**驱动（App 里的 `picker`：标题 / 说明 / 确认按钮文案 / 确认动作），
  两个入口共用它：会话里那颗「＋」（F-50，推给该会话的收件人）与本机页那块「拖入文件或
  文件夹，点击添加共享项」（F-20，登记走 `addShares`，与拖入悬浮球同一个落点）。
  加第三个入口不需要动选择框本身。
- 选择框**一律允许多选**：挑一个就是单发，挑多个合并成一条推送 —— 多选也能只选一个，所以
  不需要"允许多选"这种开关（那是白加一次操作）。
- **选中集只有一个呈现处：底部角标点开的购物车**（所有情况都走它，不区分是否跨目录）。
  跨目录累积的代价正是"换了目录之后，之前选的在列表里一个像素都不占"，所以那辆车必须
  看得到全量、能逐项摘、能全部取消。两条约束：
  - **换目录不自动展开**（换目录本来就是为了接着选东西，展开会挡道）：只把车收起来，角标照挂。
  - 车上每行带「在哪选的」—— 勾选那一刻记 `cwd` / `crumbs`，**不在提交时从 `path` 反推**
    （与上面「前端不拼路径」同一条）；两个目录里的同名文件只靠名字分不开。
  车占**布局高度**（列表是 `flex: 1`，自己让位），不做浮层：`.picker` 是 `overflow: hidden`，
  浮层会盖住列表最后几行，挂到框外还会被裁。
- 后端只负责枚举：`fs_drives`（设备与驱动器）与 `fs_list`（一层目录 + 面包屑）。
  **路径语义只在这一份实现里**（盘根必须带尾分隔符 —— `C:` 在 Windows 里是"C 盘上的当前
  目录"；面包屑的父子关系由 `Path::ancestors()` 保证），前端只把后端给过的 `path` 原样送回来，
  不自己拼路径。失败时错误里也带着 `crumbs`，所以"打不开的目录"照样能退回上一级。
- **「常用」默认是空的**：只有用户右键目录攒出来的那几条。没有"默认常用目录"这种东西 ——
  别人机器上的桌面/下载未必是你要推的，塞几条默认项只会让人每次都要绕开。
  这几条**存在配置文件里**（`config.toml` 的 `pickerFavorites`，命令 `list_picker_favorites` /
  `set_picker_favorites`），不是 webview 的 localStorage：它和共享项一样是用户数据，该躺在
  同一个数据目录（备份/迁移/清理是一个动作），也不该因为清一次站点数据就凭空消失。
  写入是**整份替换 + 立刻落盘**：右键加一下就要算数，不能等到退出时才写。
- 列举与走查只滤**三类**，判据是**同一份**（`unsendable.rs`：选择框列目录、发送前建清单都从
  这里问）—— 列出来却推不动比不列更坏：
  1. **卷根上的系统项**：`$RECYCLE.BIN`、`System Volume Information`、`Config.Msi`、
     `$WinREAgent`、`Recovery`、`pagefile.sys`/`hiberfil.sys`/`swapfile.sys`… 不是用户放的
     资料，点进去还多半是「拒绝访问」。**只在卷根按名字匹配** —— `D:\backup\Recovery` 是
     用户自己的目录，同名也不该被藏掉（macOS 那边是 `.Spotlight-V100`/`.fseventsd`/
     `.Trashes` 这类，Linux 是 `lost+found`/`.Trash-*`）。
  2. **链接**（符号链接 / junction / macOS 别名）：会**回环** —— `%LOCALAPPDATA%\Application
     Data` 就指向自己的父目录，跟随它等于把同一棵树翻好几百遍；`C:\Users\All Users`、
     `Documents and Settings` 同理。
  3. **OrbDrop 自己的数据目录**：里面装着全部设备的 token（`credentials.dat`）。
  其余隐藏项（`.git`、`AppData`）照旧可见 —— 与 `/tree` 不同（那个是给对端看的，跳过点开头的
  项），选择框是"我要推哪些东西"，隐藏的真实文件也得能选到。
- 走查遇到这三类以外的**读不到的项**（ACL 拒绝、刚好被删）**跳过 + 计数**，不再让一个子目录
  拖垮整批；跳过的项数一路带到卡片上（「已跳过 N 项（链接 / 读不到）」）—— 清单少了东西却
  不说，用户会以为"就这些"然后推漏。但**用户点的那个源**读不到仍然整条失败：界面得说出
  "这个目录读不了"，顶层源是链接/系统项也当场报错，而不是悄悄跳成一个空清单。
- 「常用」加多了会横向溢出（那一栏不画滚动条）：**拖动横滚 + 滚轮横滚**由 `$lib/scrollRail.ts`
  统一提供，标签栏用的是同一份实现 —— 两条轨道的交互必须一致，各写一套就会有人踩错
  （"加多了以后后面的点不到"就是这么来的：Chromium 只给 Shift+滚轮、触控板横滑、键盘聚焦）。
  新加的那条会自己滚进视野（右键加完"看着什么都没发生"是同一类毛病）。
- **右键菜单的定位**（贴指针出现、空间不够翻到左上、四周留 8px）同样只有一份实现：
  `$lib/ctxPlacement.ts`。面板里的菜单（`.ctx`，fixed，参照系是视口）和选择框里的菜单
  （`.picker-ctx`，absolute，参照系是这一层）只是把各自的**指针坐标 + 允许占用的区域**交给它，
  菜单**真实尺寸**由它现量（项目数差得远：设备菜单两条、行菜单两条、以后可能十几条，
  按"约 200×250"估必然会顶出边界）。新增菜单照旧只要 `use:ctxPlacement={{ x, y, bounds }}`。

### 清单与落盘（路径就是"对端看到的样子"）

```
清单里的相对路径（= 对端落盘路径）      本机绝对路径
A.txt                                → C:\…\A.txt                单文件
D/报告.txt                            → C:\…\D\报告.txt           单目录
甲目录/报告.txt                        → C:\…\甲目录\报告.txt       多选
散文件.txt                             → C:\…\散文件.txt
```

- 每个源用**自己的名字**当顶层路径；**同名源**自动去重，编号插在扩展名前面
  （`报告.txt` → `报告 (2).txt`），扩展名不变。
- 对端只做一件事：把清单里的每条路径落到 `<下载目录>/<发送方名>/` 下面。**没有"推送名
  子目录"那一层** —— 直接传多文件就是多文件，不是在目录里（`A.txt/A.txt`、`3 项/a.txt`
  那种嵌套不符合直觉）。
- `name`（推送名）只剩显示用途（通知/卡片里"推的是什么"）：单源 = 它自己，多源 = 这批源的
  共同父目录名，跨目录/跨盘取不到就用「N 项」；**它不参与落盘路径**。
- 服务端不再"拼根目录"，而是按 `sources` 表**精确查表**取文件 —— 清单里没有的路径取不到，
  `../` 之类越界路径自然也不在表里（这张表是发送方按自己选中的源建的）。

### 推送通知的交互（前端）

**通知只有一组**：面板**右下角**的气泡组（`.notif-group` / `.notif-bubble`），五种东西同形：

| 气泡 | 里面有什么 | 什么时候消失 |
|---|---|---|
| 未绑定的邀请 | 文件名 + 「拒绝」「接收」 | 点了 / 60s 自动拒绝 |
| 正在接收 | 进度条 + 「取消」 | 传完 → 变"已收到"；取消/失败 → 变"失败" |
| 发送中 / **等待对方同意**（发送侧） | 进度条 + 「取消」（传完转绿、3 秒后自己收掉） | 传完 / 取消 / 失败 |
| 发送中（**一批多台**） | 聚合进度条 + 实时计数「成功 x · 等待 y · 失败 z」+ **每台一行**（状态/百分比/逐台 ✕）+「取消全部」 | 全成 → 3 秒后自己收掉；有台没成 → **点「知道了」才消失** |
| 已收到（`done`） | 落盘位置 + 「知道了」 | **点「知道了」才消失**（长通知） |
| 接收失败（`failed`） | 原因 + 「知道了」 | 同上 |

形状统一：右对齐、**宽 = 面板的 2/3**（448 × 2/3 ≈ 300，不占满）、多条垂直堆叠、新的贴最下缘
（`column-reverse` 的 `panel-bottom` 里**靠前的 DOM 元素贴底**，通知组写在最前；组内顺序是
"通知在前、发送侧进度卡在后"—— 通知贴角）。

一批多台那张卡（`push://batch` 的快照直接渲染，界面不做聚合运算）：

```
┌──────────────────────────────────────────────────────┐
│ 推送给「工作站」「笔记本」等 3 台设备          65%   │ ← >2 台才用「等 N 台设备」；悬停列全名单
│ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░                       │ ← 聚合条：分母只算还活着的台（失败整条不计）
│ 成功 1 · 等待 1 · 失败 1              13.0 MB / 20.0 MB │ ← ★ 那两个实时数字
│ ──────────────────────────────────────────────────── │
│ ● 工作站    已发送 10.0 MB                            │
│ ● 笔记本    传输中 30%                        [✕]     │ ← 只有还在路上的行有 ✕
│ ● 台式机    失败：「台式机」不在网上，推送未发送       │
│                                       [取消全部]      │
└──────────────────────────────────────────────────────┘
```

- **单台那一批（`targets.length === 1`）保持原样**：标题/元信息（`→「X」· 局域网`）与收尾
  （toast + 3 秒自动收 / 失败立刻收）与多目标推送出现前**一字不差** —— 高频路径不该因为多目标那条路变样。
- 行文案的一处必须区分：已配对的目标**不问同意**直接收，所以它那一行说「等待开始（对方自动接收）」
  而不是「等待对方同意」（对面根本没点过任何东西，说成"等同意"是在编一个没发生的事）。
- 每台的百分比 = 该台已收 ÷ **每台的总量**，而每台总量 = `total / (done + waiting)`：
  分母必须带上已完成的那几台（它们仍在 `total` 里），只用 `waiting` 会把它们的量摊到剩下
  这几台上，某台传到一半会显示成 15%（实际 30%）—— 这个 bug 是 UI 冒烟验证时抓到的。
- 超过 5 台时先只列 4 行 + 「还有 N 台 ▾」就地展开（卡片自己不滚：滚动归 `.notif-group`，
  两条滚动条会打架）。
- 角标：**一次多目标推送算一件事**（`notifCount = notices + batches`）—— 点了 8 台也不该让
  悬浮球上的数字变成 8。

> **滚动区域夹在两条横线之间**：`.notif-group` 的盒子（= 滚动容器的剪裁边界）**上下边就是**
> 标签栏下缘与 footer 上缘 —— 底边靠 `bottom: var(--foot-h)` 贴住 footer 上缘那条线，
> 高度靠 `--notif-max-h`（App 量出来 = 两条线的距离）。所以**滚动时内容也越不过线**
> （以前为了让 17px 的阴影有地方落，盒子往下探了 17px，滚动中气泡能从线下面溜出来）。
> 左右 12px；放不下才在组内滚（**`scrollbar-width: none`，不画滚动条**，滚轮 + 每次滚到底照常）。
>
> **阴影的余量留在盒子内部**：`.notif-group` 自带 `padding: 5px 10px 10px 0`（右侧配
> `margin-right: -10px` 把边界往面板边借 10px，气泡右缘仍是 12px）。这几处数字不是拍脑袋：
> 气泡用的是**更紧的** `--shadow-bubble`，实测可见半径（渲染后逐像素扫到残差 ≤1/255）
> **左右 6.4 / 7.2、下 9.6、上 4** —— 正好收进上面那几个 padding。改动这几个数必须重新量：
> 截图 → 页面里把图贴到 canvas → 从气泡边界向外扫到"恢复纯白"的距离。
>
> **阴影点击穿透**：`box-shadow` 属于"墨迹"不属于命中区，唯一会挡住它的是容器自身的盒子 ——
> 所以 `.panel-bottom` 与 `.notif-group` 都是 `pointer-events: none`，只有 `.notif-bubble` /
> `.toast` 自己 `auto`。footer 上的铃铛、气泡之间的空隙都点得穿。

```
收到 push_invite 时：
  - **不主动弹面板**：不抢屏幕 —— 悬浮球左上角的橙色数字就是要不要点开的信号。
    未绑定 → 右下角一条气泡（带接收/拒绝）；已绑定（`auto: true`）→ 后端已经开收，
    气泡直接是"正在接收"
  - 悬浮球**左上角**的橙色数字 = 组里还剩几件事（通知 + 在途推送；与右上角的
    「长连接设备数」对称，同一个数也挂在 footer 上的铃铛角标里）：
      接收中 → 原地推进度（进度条 + 「取消」）
      完成   → 变成**待确认**的气泡，直到点「知道了」（或按「打开目录」）：
        ┌──────────────────────────────────────┐
        │ 已收到「PC-A」的推送（3 项）    48.2 MB │
        │ 3 项 已保存到 C:\…\Desktop\PC-A        │
        │                    [打开目录] [知道了] │
        └──────────────────────────────────────┘
      失败   → 同样留在气泡里（原因写在正文；没落盘位置，没有「打开目录」）
```

> **动效**：整组用 `fly` 甩入/甩出（`in`/`out` 都挂），来新的一条也各自甩进来（按序号错开
> 30ms）；`prefers-reduced-motion` 下时长归零（动效可以省，收/展与确认的功能不能省）。
> 弹窗容器必须 `overflow-x: hidden` —— 气泡甩入时先落在组外，这一轴若算成 `auto`，
> 动画期间会冒出一条横向滚动条。
>
> **铃铛**在面板最右下角（footer 里、版本号右边），点一下收起/展开整组；**收起 ≠ 已读**：
> 角标照旧挂着。放不下时只在组内滚（**不画滚动条**），App 每次把它滚到底。
>
> **"已收到"这条通知必须带落盘位置**（后端在 `push://done{completed}` 里给 `dest`）：
> 只说"收到了"的通知，点完「知道了」就再也找不到东西在哪。
>
> **「打开目录」在「知道了」左边**（只有带 `dest` 的那条才有）：按它 = 把落盘目录交给系统
> （`open_path` 命令 → 资源管理器打开那个目录），**并且和「知道了」一样撤掉这条通知** ——
> 按完还挂着一条同一个目录的气泡没有意义。开不起来（目录已被移走/删掉）则**留住**这条并
> 用提示说明原因：这条通知存在的意义就是"东西落在哪"，不能在什么都没打开时把它抹掉。
>

## 10. WS 心跳与掉线检测（N-05）

```rust
// ws/heartbeat.rs
// 每个 WS session 独立心跳

const PING_INTERVAL: Duration = Duration::from_secs(30);
const MAX_MISSED_PINGS: u32 = 3;

// 服务端每 30s 发 ping，客户端回复 pong
// 连续 3 次 ping 无 pong → 判定离线
//   - 标记 peer offline（WS 事件推送其他设备）
//   - 释放 session 资源
//   - 后台启动重连计时器（指数退避：5s, 10s, 20s, ... max 60s）

// 重连后：
//   - 重新建立 WS
//   - 中断的推送 job 尝试续传（如果接收方还有 resume 记录）
//   - 设备标签恢复在线状态
```

**拨号重试策略（`ws::spawn_outbound_link`，实测踩过 10060 才定的）**：

| 触发拨号（证据） | 节奏 | 何时停 |
|---|---|---|
| 用户点「连接」（`ensure_link_now`） | 不限次，5→60s 封顶退避（带 ±20% 抖动） | 用户点「断开」 |
| 启动恢复（`restore_links_on_startup`）/ 身份迁移接回（`restore_link`） | 先连试 **5 次**（5/10/20/40/60s），之后**待命** | 见右侧两行 |
| **对端重新出现在网上**（探活离线→在线、mDNS 重新发现 → `redial_if_remembered`） | 同上预算，秒级触发（不用等 15s 轮询） | — |
| 链路刚断（几秒前还连着） | 失败计数清零，重新享受完整预算 | — |
| 探活判离线且预算用尽 | **待命**（`LinkState::Waiting`）：每 15s 看一次在线状态，不发 TCP | 对端一上线立即恢复 |

**停止条件只有明确拒绝**（`stop_reason_for`）：403 = 对端点过「断开」→ `Stopped{PeerDisconnected}`；401 = 它不认我们的 token（清过数据/已解除配对）→ `Stopped{TokenRejected}`；本机点「断开」→ `Stopped{LocalDisconnected}`。网络类错误（连接被拒/超时/DNS/reset）**不算停手**，继续退避重试；凭据文件读失败也算"这次尝试失败"（瞬时故障不能让循环永久退出 —— 那正是"重启后接不回来还不报错"的成因）。

**为什么这样最好（四条不变量）**：

1. **不会死锁**：门控用的探活是双向的（`/pair/info` 公开端点，双方各探各的），所以"双方同时重启 / DHCP 换地址 / 防火墙授权窗口过了"这些场景里，只要双方 App 都开着，至少一侧会看到对方并动手；加上"谁没忘这次长连接谁拨"（记忆双向写入），不需要无限死磕。
2. **不对空气发 TCP**：对端关机的那些分钟里每次拨号都要等满 TCP 超时（Windows 上就是 `os error 10060`），现在压成"每 15s 一次内存里的在线标记检查"。
3. **不会静默失败**：每个状态都能自证，并且**透出到界面**——`list_devices` 带 `linkState`（`connected|retrying|waiting|stopped{reason}`），设备行显示"重连中… / 等对端上线 / 对端已断开 / 需重新配对 / 已断开"，悬停给出下一步该做什么。
4. **资源有界**：每设备一个常驻任务、稳态一分钟一次连接尝试封顶、日志前 5 次 warn 之后降级 debug。

> 反例（都不要）：无限重试 = 对空气发 TCP + 日志噪音；硬上限后彻底不管 = 上面第 1 条的三个场景变成静默死胡同；"谁 device id 小谁拨" = 项目已明确拒绝（F-16），且双拨已被多会话支持消化。

```rust
pub fn enable_autostart() -> Result<()> {
```

### Step 1：mDNS 发现


可行验证：启动两个实例，设备标签中互相出现对方。

### Step 2：WebSocket 信令（长连接）

```
ws/session.rs + heartbeat.rs + events.rs
1. 升级 WS /events 路由（握手查询参数 ?token=xxx 携带设备身份）
2. 连接池：每设备一条长连接；设备状态以真实 WS 会话为准（`WsManager::has_connection`）
3. 长连接**只由用户点「连接」或启动恢复建立**（F-16）：配对只确立"已配对"关系，不碰链路。
   - 配对完成、mDNS 发现、5s 探活 —— 一律**不拨号**（前两条只补齐地址/在线状态）
   - 任一台点「连接」= `ws::ensure_link_now`：带 `manual=1` 拨号；被拨号的那一侧、
     两端同时点、对端点过「断开」，都能靠这条路径连回来
   - **启动恢复** = `ws::restore_links_on_startup`（`lib::setup_server_task` 里调用）：
     地址簿里 `paired && autoConnect` 的设备逐个拨回来，**不带** `manual=1`（本机自己的
     记忆，不替对端解除它的「断开」）。地址还没到就等——拨号循环拿到地址（mDNS/探活）
     再接上，所以对端晚上线也没关系
   - 长连接意图的落点是地址簿条目的**一对**字段：`auto_connect`（本机要不要主动拨）
     与 `paused`（接不接对端的自动重拨）。两者是同一个意图的两面，唯一写点是
     `AppState::set_link_intent`（`LinkIntent::Wanted` / `LinkIntent::Paused`）——
     分头写早晚写出"本机不拨、却照收对端的自动重拨"。写点在**事情发生的那一刻**
     （链路建立：出站会话 `spawn_outbound_link`、入站会话 `run_inbound_session`，两侧
     对称；点「断开」：`disconnect_peer`；点「连接」：`connect_peer`；对端带 `manual=1`
     拨进来：`events_ws_handler`），不是退出时 —— 强杀进程/断电/任务管理器结束都不会丢
   - 「断开」= 断链 + 本机暂停（`WsManager::pause` / `set_link_intent(Paused)`）：
     **连接由单任务持有**，丢掉事件发送端即关掉 socket，对端立刻看到掉线；此后对端那个
     拨号循环的重拨被 `events_ws_handler` 拒（403），否则点"断开"一秒后就被对端撤销。
     **暂停必须一起落盘**：本机自己是安静了（`auto_connect` 已清），可对端没点过断开、
     它那份记忆照旧，一看见本机回到网上就拨过来 —— 暂停只活在内存里的话，重启就等于
     把「断开」撤销（本机照收那条链路，被拨号的一端还会顺手把 `auto_connect` 写回来，
     此后每次重启都自己连）。`AppState::new` 启动时把它读回 `WsManager`，设备行的
     `linkState` 同时回到 `Stopped{localDisconnected}`（界面说得出"为什么它不自动连"）
   - 配对请求仍带回来源 IP + 对端自报端口（`peerPort`）：地址先补齐，
     所以即使从未见过对端，点「连接」也能立刻拨出去
4. 心跳 ping/pong 循环（30s）
5. 会话登记（`WsManager`）：`peer_id → 会话列表`，每个会话带 generation，
   **只有自己那份能被自己注销**；「有链接」= 列表非空、发送取最新会话。
   这样即使两端同时拨号（双方同时点「连接」）也可以共存，而不会出现
   "新会话挤掉旧会话 → 旧会话关闭 → 对方拨号循环立刻重拨"的 10Hz 连-断狂闪；
   拨号循环在**已有链接时只等待不重拨**，避免堆积无用 socket。
6. 设备状态变化（未绑定/已配对/长连接）通过 Tauri 事件同步到前端：
   `list_devices` 返回 `connected`（WS 会话在否），会话建立/断开两侧都 emit
   `devices://changed`
```

> 长连接的入口只有两个：**用户点「连接」**、以及**启动时恢复上次的长连接**——配对只完成 token 交换、把设备变"已配对"，不碰链路，没有"id 较小的一方自动拨号"，也不会因为 mDNS 发现/5s 探活就后台拉起。界面上"长连接"= WS 会话在，不是"HTTP 可达"。链路断了之后，当初点「连接」的拨号循环按指数退避继续重连（用户要的会话该被保住）；本机点「断开」则连它一起停掉、并拒掉对端重拨，任一台点「连接」即可恢复。
>
> 后台任务的启动一律走 `task::spawn`（没有 Tokio 运行时则记录并跳过）：Tauri 的**同步**命令跑在主线程，直接 `tokio::spawn` 会 panic 掉整个进程（点按钮"闪退"）。
>
> 文件日志的 `WorkerGuard` 存在静态里：它被提前 drop 就等于提前结束刷盘职责，日志文件会一直是 0 字节（出问题时没有任何线索）。
>
> 两条硬规矩：`/pair/info` 只报**实际监听端口**（端口被占会顺延到 +1..+10，报配置值等于让对端去连别的进程）；**单实例**用 `tauri-plugin-single-instance`（OS 级锁，进程退出即释放）—— 第二份进程把已在跑的实例调到前台并 emit `orb://show` 让面板展开。**绝不能**让第二份进程自己静默 `exit`：那在用户侧就是"启动一下就闪退"，而且日志都来不及落盘。
>
> **长连接必须带能反解出身份的 token**：`/events` 没有"本机还没配对过任何设备就放行"的后门 —— 那个后门会让刚被解除配对的对端拿旧 token 连上、还被登记成本机的 `self`（对端显示"长连接"，本机却把它当"未绑定"）。旧版对端本地仍存着 token 时，本机一律 401 拒绝它的 WS 与 HTTP。

可行验证：`tests/p1_integration.rs` —— 配对后（地址/token 都齐）**不许**自己建链、点「连接」才建链、被拨号方断开后双方掉线、断开方/对端点"连接"都能恢复、对端重拨被拒、重连后链路稳定（含两端同时点「连接」）、**重启后按磁盘记忆自动接回长连接（点过「断开」的不接，且对端的自动重拨照旧被 403 拒）**、**对端当时没上线时自动恢复先失败、对端上线后不点任何按钮自己接回**、`/pair/info` 报实际端口、没有运行时点按钮不 panic。重试预算的边界（用户点「连接」不受限 / 自动够 5 次且对端不在线则待命 / 对端一上线即放行）由 `ws::tests::auto_dial_backs_off_once_the_budget_is_spent_and_the_peer_is_absent` 钉住。

## 15. 拖拽下载（F-46）

把树里（本机共享项 / 对端共享项）的**任意文件或目录**拖到资源管理器/Finder 的某个目录里，
内容直接落在那个目录；拖目录 = 整个目录含子目录与文件；落下的动作**只可能是复制**。

### 为什么必须是原生拖放

网页里的 HTML5 拖拽（`draggable` / `dragstart`）出不了 webview：目的地（资源管理器）是
**另一个进程**，只有 OS 的原生拖放跨得过去。所以前端只负责**认手势**（`src/lib/dragOut.ts`
只做"按下 + 移动过阈值"的判定），起拖由 Rust 侧发起：`DoDragDrop`（`src-tauri/src/drag.rs`）。

### 三种内容，三条路

| 源 | 数据格式 | 内容从哪来 |
|---|---|---|
| 本机共享项 | `CF_HDROP` | 磁盘上的真实路径，资源管理器直接复制 |
| 对端项·**小**（单文件 ≤ 100 MB、目录总量 ≤ 500 MB） | `CF_HDROP` | **起拖前**整份下到暂存目录（`<数据目录>/staging/<uuid>`），交出去的就是那份真实路径 |
| 对端项·**大** | `CFSTR_FILEDESCRIPTOR` + `CFSTR_FILECONTENTS`（虚拟文件） | 自实现的 `IStream`，**落下那一刻**才按需从对端拉（`GET /file?offset=&len=`） |

**为什么小项要提前转存**：虚拟文件是 shell 协议，只有资源管理器 / Chromium 系 / QQ 这一小撮
实现；**只认 `CF_HDROP` 的应用（微信这类）根本不问 `FileContents`**，给虚拟文件它永远收不到
（实测：微信只问 `CF_HDROP`，落点提示却照样亮）。真实路径这条路才通吃。代价是起拖前要等内容
下完 —— 拖放循环跟着**按住的主键**走，用户得按住等 —— 所以用上限兜住等待时间。超过上限的仍走
虚拟文件：大目录照旧秒起拖、不落暂存盘，只是只有支持虚拟文件的目标能收。

暂存目录**不能拖完就删**：`CF_HDROP` 落下后资源管理器可能仍在**异步**复制（进度框一出来
`DoDragDrop` 就返回了）。留 `STAGE_TTL`（6 小时），下次拖拽与启动时按龄清扫
（`drag::sweep_staging`）。

> 早期版本是"先递归下到暂存目录、再拖副本"，为的是绕开"跨进程编组拿不了自定义 `IStream`"
> 的顾虑。**实测这个顾虑不成立**（探针：真手势 + 真资源管理器，内容直接写进目标目录），
> 于是大项改成了虚拟文件；小项后来又退回转存 —— 不是为了编组，而是为了覆盖只认
> `CF_HDROP` 的应用（见上）。

### 时序（为什么分两步）

拖放循环跟着**按住的主键**走，所以是"先备齐、再起拖"：

1. 前端：按下 + 移动过 6px → `prepare_drag_out` 登记票据；对端项同时开始走目录（元数据）。
2. 前端：`start_drag_out` → 等元数据备齐（本机项立即就有）→ 确认主键还按着 →
   `run_on_main_thread` 里跑 `DoDragDrop`（它自带模态循环，阻塞主线程直到拖放结束）。
3. 落下之后票据就丢；`Read` 失败（对端掉了）会让资源管理器报复制失败，不做重试。

### 实测踩到的坑（别按直觉改）

- **`formatetc.tymed` 是位掩码**，不是枚举：资源管理器要文件内容时给的是
  `13`（`ISTREAM | ISTORAGE | HGLOBAL`）。按等号判会把这种请求全部打回 `DV_E_FORMATETC`，
  表现是"目录建出来了、文件一个都没复制"。
- **枚举表里列了什么，`GetData` 就必须给得出来**：目录项也要在 `CFSTR_FILECONTENTS` 里
  出现，并且要给一个**空流**（内容为 0 字节的 `IStream`）—— 只列不交付会让协商卡住。
- **`QueryContinueDrag` 的返回值**：Esc → `DRAGDROP_S_CANCEL`；主键松开 → `DRAGDROP_S_DROP`；
  否则 `S_OK`。一直回 `S_OK` 时循环**不会结束**（主线程卡住）；而一进循环就回
  `DRAGDROP_S_DROP`（键状态没读到按下）则当场"落下"、什么都不发生 —— 判据是
  `grfKeyState` 里的 `MK_LBUTTON`，它是**本线程消息队列**里的键状态。
- **`DoDragDrop` 跑在哪个线程很关键**：必须在**窗口所在线程**（本应用＝Tauri 主线程）
  且该窗口是**前台窗口**。实测在 tokio 工作线程上、或前台窗口是别的进程时起拖，
  拖放循环一动不动（连一次 `QueryContinueDrag` 都收不到）。
- **只给 `DROPEFFECT_COPY` 还不够**：同一块盘内拖拽的默认动作是"移动"，所以数据对象同时
  提供 `Preferred DropEffect` = COPY，资源管理器才会复制而不是把源文件搬走。
- **`GMEM_MOVEABLE`**：`CF_HDROP`/描述符这两块 HGLOBAL 必须是可移动内存，跨进程编组的要求。
- 落下后资源管理器会调 `SetData`（`DropDescription` / `DisableDragText` …）并忽略失败，
  源侧一律回 `E_NOTIMPL`，复制本身照常完成（实测）。
- **`prepare_drag_out` 必须是 async 命令**：对端项要 `task::spawn` 一个走目录的任务，而 Tauri
  的同步命令跑在主线程（那里没有 Tokio reactor），`task::spawn` 只会记一行
  "no tokio runtime here; task skipped" 就跳过（同 `connect_peer` 的注释）。同时
  `DragStore::prepare` 在 spawn 失败时当场把票据判失败，让界面立刻看到原因。
- **`/shares` 的 `isDir` 必须是真元数据**，不能拿"名字里有没有点"猜：没有扩展名的**文件**
  被报成目录后，对端一点开就是 `Path is not a directory`，拖拽也会被当成目录走。
  （本机那条同名猜测 `types.ts::shareIsDir` 已经删掉：`list_shares` 现在也回真 `isDir` ——
  它同时决定「本机」标签页与悬浮卡片的图标/展开箭头，猜错的代价只是显示，但那是白给的真值。）
- **别信前端带来的 `is_dir`**：它是别处的判断（对端 `/shares`、树里那条记录），可能过时。
  起拖前真去问一次对端（`/stat`），以对端为准；对端说"不是目录"而我们在走目录时，
  退化成"拖这一个文件"而不是把用户卡在一句错误上。
- **对端版本可能旧**（没有 `/stat`）：那就退回"列父目录再挑出那一条"（`/tree` 哪个版本都有）
  拿大小/时间/是否目录。两条都问不到时：共享项根按调用方的判断走、大小未知
  （描述符里不写 `FD_FILESIZE`，内容照样读到流末尾）；**非根路径则判失败** ——
  不能被越界路径（`../x`）骗过去，否则拖拽"看着成功"、复制到一半才报错。
- 非 Windows 还没有原生拖放源（macOS 要走 `NSDraggingSession`），这时接口返回明确错误。

### 服务端

拖单个**文件**时 `FILEDESCRIPTOR` 要报出它的大小与修改时间，而 `/tree` 只列目录、
对"共享项根就是一个文件"的情况直接回 400 —— 所以补了 `GET /stat?share=&path=`
（协议草案里本来就有这个端点），返回 `{name, isDir, size, modified}`。

### 校验

```bash
cargo test --offline drag::                 # CF_HDROP 字节布局、描述符布局、数据对象接口面、路径/名字
cargo test --offline --test drag_virtual    # 对端走目录（真 HTTP）：清单结构、单个文件走 /stat、越界拒绝
```

> 端到端的"拖到资源管理器"是 OS 的模态循环，只能合成鼠标输入来跑（本次改动就是这么验的：
> 真手势 + 真资源管理器 + 真服务端，目录树连同子目录与文件内容全部落到目标目录，
> 源目录不动、`%LOCALAPPDATA%` 下没有任何暂存）。

## 16. 托盘：状态头、在线/离线、退出（F-03）

任务栏里不再出现 OrbDrop（`skipTaskbar`），托盘于是成了这台进程**唯一的窗口外入口**，
菜单里同时管「在线 / 离线」与退出：

```text
● 状态 ▸              ← 状态头：标题只说明"这行是什么"（名词），状态由点色给
     ✔ 在线           ← 子项是**选项列表**，原生勾选 = 当前是哪个
       离线
──────────────
    退出
```

```
tauri.conf.json  app.windows[main].skipTaskbar = true     ← 窗口不进任务栏
src-tauri/src/tray.rs                                      ← 给配置里那个托盘挂菜单
src-tauri/icons/32x32-offline.png                          ← 离线那张灰图标（编译期嵌入）
```

### 为什么状态头做成子菜单标题，而不是一行禁用项

Windows 只把菜单项的**文字**画灰，位图不跟着灰（muda 走原生 `MIIM_BITMAP`，不做 owner-draw）
—— 禁用行会变成"灰字 + 鲜绿点"两套打架的信号，而且那一行点了没反应，是个死点击。
子菜单标题永远正常色、点它=展开，这两个问题都不存在。

### 状态头为什么是"名词 + 点"，不写状态名

标题是**固定文案** `状态`（`TITLE_PRESENCE`），状态只由点的颜色说。理由两条：

- 写状态名（`状态：在线`）是在**第三次**重复同一件事：点的颜色说了一遍、子菜单的勾选说了一遍；
- 标题里出现状态名会把"状态 / 动作"的歧义请回来（那个名字看起来像可点的目标），
  而名词 `状态` 只回答"这行是什么"，语法上不会读成任何状态。

顺带的收获：标题不随状态变，`refresh` 里因此**没有** `set_text` 这一步 —— 每次刷新只动
点色、勾选、托盘图标、tooltip 四样。菜单也窄了：标题行的文字墨迹从 58px（`状态：在线`，
5 个全宽字形）降到 **23px**（`状态`，2 个），菜单从 158px 收到 **122px**（实测）。
（宽度仍由这一行决定——不是文字，而是它右端那个展开箭头。）

### 状态在**不打开菜单**时也看得见（消歧义的关键）

- **托盘图标**：离线时整颗转灰（与球心 logo 离线转 `--muted` 同一套语言，形状不动只换色）；
- **tooltip**：`OrbDrop · 在线` / `OrbDrop · 离线（对局域网隐身）`。

状态有这三处一致的外显，菜单里那两行才敢纯当选项用 —— 否则"只显示另一个状态"必然被读成
"点我变成它"还是"我现在是它"，两种读法都成立。

### 圆点：Win32 菜单文字单色，彩点只能走位图

`○`/`●` 在菜单里是黑的，emoji 在 `HMENU` 上渲染不可靠，所以点走
`Submenu::with_id_and_icon` / `IconMenuItem`（原生 `MIIM_BITMAP`）。点图**运行时合成**
（`tray::dot_rgba` → `Image::new_owned`）：零资源文件、零 feature。颜色取面板令牌换算到
sRGB —— 在线 `#009554`（`--ok`）、离线 `#6a6f76`（`--muted`）。

- 离线点**刻意不用**面板里那枚「离线」点（`color-mix(in oklch, var(--fg) 22%, transparent)`）：
  那个值是为面板自己的浅色底配的，而**菜单底色跟随系统浅/深主题** —— 几乎透明的深灰放到深色
  菜单上会直接消失。中灰在白底、黑底上都看得见。
- 尺寸跟随 DPI（`dot_slot`，逻辑 16px → 16/20/24），边缘 4×4 超采样抗锯齿。

### 灰图标**不需要** `image-png` feature

`tauri::include_image!` 是**编译期**解码（tauri-codegen 把 PNG 落成 RGBA 缓存，宏展开成
`Image::new(include_bytes!(cache), w, h)`），只要求源图是 **RGBA**（不是就 panic）。
`image-png` 是运行时 `Image::from_bytes` 的门槛，这条路用不到。代价：`tray::tray_icon()` 里
那两张图必须与配置的 `trayIcon.iconPath` 保持一致。

### 单一实现 + 双向同步（不是可选项）

- `lib.rs::apply_online` 是**唯一**的切档入口，命令（面板）与托盘菜单都调它：副作用有
  mDNS 注销、断链、落盘三样，多一份实现必然漏一样。
- 托盘必须监听 `local://online`（面板也能切），否则两处显示分叉；刷新一律现读
  `state.is_online()`，不信任何缓存。
- 句柄 `TrayHandles` 存在静态 `Mutex<Option<_>>` 里，但**取副本、绝不把 guard 带到菜单调用
  之后**：`set_text`/`set_checked`/`set_icon` 内部是 `run_on_main_thread` + 等回执，握着锁等
  主线程 = 主线程反过来等这把锁就死锁。

### 实测的四个坑（别按直觉改）

- **`skipTaskbar` 走的是 `ITaskbarList::DeleteTab`**（tao `set_skip_taskbar`）：只摘任务栏按钮，
  不碰窗口样式（所以不影响 `strip_os_frame` 的 DWM 处理，也不动 Alt+Tab 那一套）。
- **muda 的 Check 项被点击时会先自己反选**（`menu_selected` 里 `set_checked(!item.checked)`）
  才派发事件：点"当前那一项"会留下一个假空勾。而状态没变时 `apply_online` 早退、**不发事件**，
  所以事件驱动的刷新救不了它 —— 处理完必须**无条件**重刷（实测：点当前项后重开菜单，与干净
  菜单**逐像素相同**；对照组的在线/离线菜单差 50/156 像素，证明这个比较不空转）。
- **溢出面板开着的时候，新注册的图标不会补进去**（shell 老毛病）：关掉再开一次才看得见。
  托盘图标默认就落在 Win11 的「显示隐藏的图标」溢出面板里，不是直接摆进托盘区。
- **托盘按钮的 UIA 名字是两行**（`OrbDrop` + 换行 + tooltip），而 `-like "OrbDrop*"` 的 `*`
  **不跨换行** —— 换了 tooltip 之后按名字找图标要用 `-match "^OrbDrop"`。

### 退出必须自己刷日志

`AppHandle::exit` 最后落到 `std::process::exit`：**静态量不会被 drop**，`log.rs` 里那个
`WorkerGuard` 的刷盘职责就此消失 —— 最后几行（包括"谁把进程关掉的"）会连着非阻塞队列一起
没了。所以退出路径先 `log::flush()`（`Mutex<Option<WorkerGuard>>` 取出来丢掉 = 关后台线程 +
刷盘）再 exit。实测：退出后日志最后一行就是 `托盘菜单：退出 OrbDrop`。

### 校验

```bash
cargo test --offline tray::     # 点边长跟随 DPI、圆心不透明/四角透明、软边与覆盖度≈圆面积
```

端到端只能合成输入跑（无边框窗口连关闭按钮都没有，"退出"是唯一出口，必须真点一次）：

1. **任务栏**：UIA 枚举 `Taskbar.TaskListButtonAutomationPeer`，断言没有 `OrbDrop*` 按钮
   （**按钮的 UIA ProcessId 是 explorer 的，不是应用的**，只能按名字判）。对照：改动前的旧
   二进制在同一台机器上会多出 `OrbDrop - 1 个运行窗口`。
2. **托盘**：打开溢出面板 → 找到名字以 `OrbDrop` 开头的 `SystemTray.NormalButton` → 合成右键 →
   悬停第一行展开子菜单。菜单是原生 `#32768`，**UIA 读不到菜单项文字**，所以按像素验：
   8×8 那颗点（在线 44/64 绿、离线 44/64 灰，几何完全一致）、子菜单勾选列（勾在 在线 12 暗像素 /
   离线 0，反之亦然）、托盘图标（蓝 饱和 170 / 灰 饱和 10）。
3. **两个入口都要走**：托盘切、面板右上角状态框切 —— 后者断言 tooltip 跟着变，证明
   `local://online` 监听器在起作用；两条路在日志里都应留下
   `mDNS service unregistered (offline)` / `dropping link` / `local presence changed`。
4. **退出**点到底：进程退出码 0、日志留下退出那行。

## 17. 移动端参考设备与视口比例（`--u` 设计单位）

### 现象：比例差得很大，不是错觉

移动端界面全是固定 px，视觉比例只取决于**逻辑宽度**（CSS px）＝ 物理宽 ÷ (density/160)：

| 设备 | 物理 / density | 逻辑视口 / dpr | 15px 字号占屏宽 |
|---|---|---|---|
| 原型基准（`design/orbdrop-mobile-prototype.html`） | — | 390×844 | 3.85% |
| MuMu 默认（900×1600@240dpi，实测） | 900×1600 / 240 | **600×1043** / 1.5 | 2.50% |
| 手机（MuMu 720×1280@320dpi，实测） | 720×1280 / 320 | 360×616 / 2.0 | 4.17% |

同一份 CSS，600dp 那台机器上每个控件只占屏宽的 65% —— 字号、头像、行高看着都"小一档"。
**分辨率高不是原因**，`分辨率 ÷ density`（逻辑宽度）才是。

### 规则：`--u` 设计单位（只放大不缩小）

`src/mobile/mobile.css` 的 `:root` 里：

```css
--design-w: 390;                                 /* 原型 --phone-screen-width */
--u: max(1px, calc(100vw / var(--design-w)));    /* ≥390 等比放大；<390 保持设计值 */
```

文件里所有长度都写成 `calc(N * var(--u))`（`N` 就是原型里的值）。例外见文件头注释：
`1px`/`2px` 描边与焦点环、`99px`/`999px` 胶囊圆角、`%`/`em`、`--shadow`（归颜色生成器管）。

- **不做列宽上限**：宽视口放大是一整列等比放大，仍然占满视口 —— 不会重新出现早先被否掉的
  居中列 + 左右空档（那条记录在 `mobile.css` 底部的注释里）。
- Chrome 90 下限满足：只用了 `max()`/`calc()`（79+）。**不要**引进 `@container`、`:has()`、
  `(width < Npx)` 范围语法、`svh/dvh/svmin`。

### 参考设备与换算

参考机应是**手机逻辑宽 360–390dp**；600dp 那类配置留着当"宽视口测试机"，不当参考机。
在固定物理分辨率上用 density 反推目标逻辑宽（`density = 160 × 物理宽 / 目标逻辑宽`）：

```bash
adb shell wm density 369   # 900×1600 → 390×694dp（对齐原型基准宽）
adb shell wm density 400   # 900×1600 → 360×640dp（经典手机宽）
adb shell wm density reset # 撤掉覆盖
adb shell wm size  /  wm density   # 先看当前值
```

改 density 会**重建 Activity**（`AndroidManifest.xml` 的 `configChanges` 里没有 `density`），
应用重启、页面状态清空是预期行为。优先在模拟器自己的设置里改分辨率+dpi（MuMu 现在就是
720×1280@320dpi，没有 `wm` 覆盖）。

### 零代码实测配方（读真机视口的真值）

```bash
PID=$(adb shell pidof com.x177plus.orbdrop | tr -d '\r')
adb forward tcp:9222 localabstract:webview_devtools_remote_$PID
# 读 http://127.0.0.1:9222/json/list 拿 webSocketDebuggerUrl，
# 然后 CDP Runtime.evaluate：{"expression":"JSON.stringify({i:[innerWidth,innerHeight],dpr:devicePixelRatio})"}
```

A/B 时把 `dist-mobile/assets/MobileApp-*.css` 的文本原样 `appendChild` 成 `<style>`，
一次注入即可对比"产物 CSS 生效前/后"的 `getComputedStyle`（页面重载即回到未注入状态）。

### 实测结论（`--u` 落地当次）

- **360dp：零回归** —— 16 个选择器 × 10 个计算属性 + `getBoundingClientRect` 与改动前**逐条相同**。
- **600dp：比例与原型一致** —— `.cv-name` 字号 4.10%（原型 16/390）、`.av` 宽 11.79%（46/390）、
  `.icon-btn` 宽 10.26%（40/390）；`documentElement` 滚动尺寸 = 视口（不溢出、不出现空档）。
- 门禁：`npm run tokens:check` ✓、`npm run check:compat` ✓、`npm run build:mobile` ✓。
  注意 `mobile.css` **必须保持 LF**：生成器按整文件字符串比对，CRLF 会误报"回退未同步"。

## 18. 中转：为被 AP 隔开的两台设备盲转字节（F-106 / S-09）

> 跨网段**中转记忆**（把"哪一段设备经哪一段中转"落盘、同段泛化到 B1/B2/B3、C 掉线自动换 D、反向告知被中转的那一侧）是 **F-107 / S-10**，**已实现**：设计与算法、实现记录（含与设计的偏离、Windows 请求方那条平台限制、还没验的部分）见 `docs/relay.md`；用例见该文档 §15。
> 最近一轮真机修复（**锚点离线之后池里那台仍要拨得动** + 活回话刷新中转能力位）见 `docs/relay.md` §19。
> 再一轮真机修复（**中转记忆被"一次快照"抹掉** —— 池改为按"并"更新，来回切换锚点之后另一台仍在记忆里）见 `docs/relay.md` §21。

### 起因：不是"发现"坏了，是单播被掐了

实测环境（公司 Wi‑Fi 的企业 AP）里，两台手机在同一 SSID、同一网段，却**连 ARP 都问不到对方**
（`ip neigh` → `FAILED`）、`ping` 报 Destination Host Unreachable、TCP 握手卡在 `SYN_SENT`；
而**组播过得去** —— 对端启动时发的 mDNS 通告能让设备列表"闪一下"（解析到 → 5s 探活失败 →
判离线 → 前端隐藏"未配对且离线"的行）。跨网段反而通（办公网的 PC 经网关能连两台手机的 3890）。
结论：**AP 隔了同一网段里客户端之间的单播**。(`/discover` 的锚点那套只解决"跨段"，解决不了
"同段但被隔开"。)

### 怎么做

- **能力位**：`/pair/info` 与 `/discover` 各带一个 `relay`（= `Config::allow_relay`，S-09，默认关）。
  请求方从 5s 探活的那一次问答里就学到了（`state::probe_addr`）。
- **控制面**：`POST /relay/open`（鉴权路由，要凭据；`server::routes_relay` → `relay::open`）：
  开关关着 403、目标不合格 404、限流 429、本机开不出来 503。**资格判定在前、限流在后** ——
  否则"目标写错一次"会把接下来几秒的额度也吃掉。
  目标优先取本机地址簿里**此刻在线**的那一台；本机不认识它 / 它不在线时，退回**请求方捎来的地址**
  （`addr`），但用之前必须到那个地址问一次 `/pair/info`、确认自报的 id 就是请求方点名的那一台。
  实战教训：跨网段的中转方**够得着目标却从没认识过它**（mDNS 跨不过路由，手动加的还可能是旧 id），
  少了这一手，"手机 A 请桌面端中转去 B"会直接 404 —— 而 A 明明知道 B 的地址。
- **数据面**：中转方 `TcpListener::bind(0.0.0.0:0)`，accept 时按**来源白名单**（请求方在控制面上的
  来源地址 + 它此刻在地址簿里的地址）放行，然后连**目标自己的直连地址**（单跳，不链式），
  `copy_bidirectional` 原样搬字节（不解析、不改写）。上限 8 条、同一位请求方 3s 冷却、
  **一条活连接都没有**且 120s 没有新连接才回收；关掉开关立刻全收（`relay::close_all`）。
- **请求方**：5s 探活**恒探直连地址**（那是"直连通不通"的信号 —— 正走中转时也探，直连一恢复就
  收起中转）。判离线时 `relay::ensure_for` 挑一台"已配对 + 自报可中转 + 在线 + 自己没在走中转"
  的设备请端点（同一台设备 30s 一次），成功就把端点写进那台设备的**运行时段**（`PeerDevice::relay`，
  `#[serde(skip)]` 不落盘）；中转这一跳也不通就把端点收掉再按离线处理。
- **取址只在一处**：`PeerDevice::dial()` —— 十几处数据面（`peer_fs::coords`、推送、聊天兜底、
  BC 代理、WS 拨号…）全部经它，不许各自读 `ip`/`port`。**广播/上报类**（`/discover` 的表）仍用
  `ip`/`port`：那是"这台设备自己长什么样"，不是"本机怎么走到它"。
- **指纹**：中转端点上站的是**目标设备**，而指纹表（`net::Trust`）按地址索引 —— 端点字面量因此
  写成 **IPv4 映射的 IPv6**（`net::relay_host`，如 `[::ffff:10.198.71.106]`）：同一个地址、另一个
  键位，免得与中转方自己的服务撞成"同地址两枚指纹 → 不钉 → 退 TOFU"。`refresh_trust` 把端点键位
  一起钉上，`remember_peer_fingerprint` 记的也是**刚拨的那个主机**。
- **别把中转方的地址记成对端地址**：经中转过来的配对握手 / 聊天兜底，其 TCP 来源是**中转方**；
  `state::is_relayed_source` 一认出来就**不记拨回地址**（记了以后本机就会拿中转方的地址去拨对端，
  表现是"消息发给了一台不相干的设备"）。
- **被隔离时的两处界面后果**（与上面同源）：
  ① `AppState.seen`（mDNS 记录存续 → `note_seen`/`clear_seen`）与 `online`（探活）**刻意分开**，
  `list_devices` 多带一个 `seen` 与 `relayVia`：未配对 + 看得见 + 探不通的那一行**照常列出来**
  （否则"闪一下就没"），但**不带任何特殊状态** —— 关系没建立就是「未绑定」、点照旧按 `offline` 画；
  那句"这张 Wi-Fi 可能把客户端之间的单播隔开了"只在**发起连接**时弹（2026-09-30 改：配对 /
  长连接 / 立即连接 / 配对邀请的动作里，判据是前端 `unicastBlocked`：`seen && !online && !relayVia`，
  见 `stores/devices` 的 `unicastBlockedTip`）。中转接管后自动回到在线行并标「经 X 中转」。
  ② 消息够不着时**先当场试一次中转**（`ensure_for`，它自带限流），成了就立刻重发；仍不通就落
  「排队」（既有语义 F-95）并 `notify_undeliverable` 发 `chat://undeliverable` 给界面 —— 用户看到的
  是一句解释，而不是"发了没反应"。

### 坑

- **Windows 作为请求方**：`connect()` 一个 IPv4 映射的 IPv6 地址需要 socket 上的 `IPV6_V6ONLY=0`，
  而 reqwest/hyper 自建的 socket 不带这个标志（Windows 默认 v6-only；Linux/macOS/Android 默认双栈，
  实测手机与 PC 用 curl 都能连）。所以端点地址**优先挑"同网段里的另一块本机网卡地址"**（那样是
  普通 IPv4、任何平台都能连），只有本机在请求方网段上只有一个地址时才回落到映射形式。
  彻底解法是"指纹按设备钉而不是按地址钉"（要动信任模型），本版没做。
- **中转端点不落盘**：它描述的是"此刻有没有路"，重启/换网都该由探活重算 —— 落进地址簿会留下一串
  指向别人中转端口的死地址（`config::relay_addr_never_hits_the_address_book` 盯着这件事）。

### 校验

- 单测：`net::relay_host_is_a_distinct_pinning_key`（键位必须不同）、
  `config::{dial_prefers_the_relay_only_when_one_is_set, relay_addr_never_hits_the_address_book}`、
  `relay::{registry_enforces_the_cap, caller_cooldown_blocks_immediate_retry}`。
- 集成：`tests/p1_integration.rs::relay_open_obeys_the_rules_and_blind_forwards_bytes` —— 真起服务器 +
  真回声服务器：验 403/401/404 三档、端点字面量（`[::ffff:` 前缀）、以及字节**真的搬过去又搬回来**。
- 真机（两台手机在同一张被 AP 隔离的 Wi‑Fi 上、桌面端打开 S-09）：请求方直连探不通后经桌面端拿到
  端点、把那台设备判成在线（日志 `直连不通，改走中转` + 端点键位上的指纹钉住）；关掉开关 → 403、不再开。

## 19. 收到消息的通知（F-108）

### 目标

人没看着屏幕的时候，收到对端消息要知道（"可以做到吗，应用在后台的话" —— 可以，见下）。
一对一标题 = 设备名、正文 = 消息；群聊标题 = 群名、正文 = `发言人：内容`；点一下**直接进那条会话**。

### 为什么通知在后端发，而不是界面发

这是整件事的**唯一关键决定**。应用切到后台时，`WryActivity.onPause` 会 `webView.onPause()`
（WebView 的 JS 定时器全停），界面本身也可能被系统回收；而后端一直在收消息。通知要是写成
"前端 `listen('chat://changed')` 再调插件"，后台这一档正好是它最不可靠的那一档。

所以通知从**消息落账那一步**发出（`ws::session::handle_inbound` 的 `ChatText` / `GroupText`），
Rust → Kotlin 一路直达，不经过界面：

- `src-tauri/src/notify.rs`：一个插件句柄 + `message()`。句柄在 `run()` 里注册插件时放进
  `OnceLock`（`register_android_plugin("com.x177plus.orbdrop", "MessageNotifierPlugin")`）——
  注册发生在 `setup` 之前，句柄只能在那一刻拿，所以没走 `AppState`。
- `MessageNotifierPlugin.kt`：渠道、图标、点击要落到哪条会话，都是安卓那一侧的事。
- 桌面端 `message()` 是空操作：桌面本来就有一块看得见的面板，右下角那组气泡说的是别的事
  （推送与配对邀请），消息塞进去会把面板变成第二个通知中心。

### 三处"不该响"

1. **重复投递**：投递是"至少一次"（补发、重连重投、HTTP 到了但对端没来得及回话），同一条
   消息响两遍比不响更烦人。判据是落账那一步的返回值 —— `ChatStore::record_inbound` 现在返回
   `(bool, Snapshot)`（第一格 = 确实新记下），`group::on_group_text` 本来就返回 bool。
2. **界面在眼前**：用户正看着聊天记录，角标也跳了，再响一声只是噪音。
   `AppVisibility.foreground` 由 `MainActivity.onResume` / `onPause` 写 —— 后端只知道收到了消息，
   不知道用户在看哪一屏。
3. **没给通知权限**（Android 13+ 那次询问被拒）：`areNotificationsEnabled()` 为假时直接不发。

### 两个渠道是故意分开的

`orbdrop.keepalive`（`IMPORTANCE_LOW`、不可撤、点一下回应用）与 `orbdrop.messages`
（`IMPORTANCE_HIGH`、可撤、点一下进会话）各是一条：用户可以在系统设置里**单独关掉消息提醒**，
而"保持互联"那条照旧 —— 后台在线不跟着一起丢。

### 一条会话一张卡

通知 id = `-"orbdrop.msg:<kind>:<id>".hashCode()`：同一条会话连着来几条只更新那张卡（内容是最新
那条），不堆成一排把别的应用的通知挤下去。**取负**是因为常驻通知用的是正数 id（1701）——
撞上会把"我正在运行"那条顶掉。

### 点通知进会话：只带 `kind` + `id`

后端带 `kind`（`dev` / `grp`）+ 后端那份 id，**不带**前端那串会话键（`dev:` / `grp:`）：键的拼法
是界面的约定，后端复制一份就成了两处得同时改的东西。界面拿这两样自己拼（`chat.convoKeyOf`）。
交付走的是与返回键同一条路（原生问界面）：`MainActivity.deliverPendingConvo` 调
`window.__orbdropOpen(kind, id)`，界面回 `true` 表示进去了。

### 坑

- **Rust 叫 Kotlin 那条路会 panic，而 release 档是 `panic = "abort"`**：wry 的 `dispatch`
  在"一个 Activity 都不剩"时 `expect("no available activity")`，而本仓 `[profile.release]`
  写着 `panic = "abort"` —— 直接整个进程倒地（连前台服务一起）。所以 Rust 那边记着一份
  "界面还在不在"（`notify::set_ui_alive`，由 `Builder::on_window_event` 的
  `Destroyed` / `Resumed` 翻转），界面没了就**不去碰那条会 panic 的原生调用** ——
  消息照收、账照落，只是不再指望通知栏。
- **交付要重试**：点通知那一刻界面可能还不存在（冷启动，Rust 那侧才刚开始建 WebView），
  `window.__orbdropOpen` 是 `MobileApp` 挂上去的 —— 一次调用会石沉大海，用户看到的是
  "点了通知，应用开了，却停在列表里"。所以每 300ms 问一次、最多约 6 秒；界面站起来就当场交付。
  试完还没成**不清掉**那个目标：下一次 `onResume` 或新的通知重新试。
- **`onNewIntent` 也要接**：Activity 是 `singleTask`，应用开着（哪怕在别的 tab）时点通知走的是
  `onNewIntent` 而不是 `onCreate`（`onResume` 也不一定再派发一次）。
- **`invoke.parseArgs` 的字段名就是 Rust 那侧 JSON 的键**（`kind`/`id`/`title`/`body`），
  少一个就抛在 Kotlin 里、Rust 只看到一句 reject。

### 校验

- 单测：`chat::tests::a_redelivered_inbound_message_is_recorded_once`（重复投递不再算"新的"，
  通知靠它去重）。
- 真机（`adb shell dumpsys notification --noredact`）：应用切到后台 → 从另一台发一条消息 →
  通知栏出现 `设备名 / 消息内容`，渠道 `orbdrop.messages`、`importance=HIGH`；应用切回前台再发
  一条 → 不再出新的通知；同一条会话连发两条 → 只有一张卡、内容是最新那条；点通知 → 应用到前台
  且落在那条会话上。

## 20. 安卓：收件里的文件点开，APK 点一下就装（F-109）

### 目标

收件（`<下载目录>/<发送方名>/…`，见 `mobile::list_inbox`）里的东西点开要用系统应用打开；
**`.apk` 那一档直接进系统安装器** —— "收到 APK 点一下直接装"。

### 原来是废的（实测，不是推断）

这一版之前，界面上那一项叫「打开」，后端 `open_path` 在移动端走 `tauri_plugin_opener`：

1. Rust 侧移动分支是 `run_mobile_plugin("open", path.into())` —— 把路径当**裸字符串**发过去；
2. Kotlin 侧 `OpenerPlugin.OpenArgs` 要的是 `{url, with}` 这个对象。

于是 `parseArgs` 当场抛。拿同构的类 + 同一个 `ObjectMapper` 实测（`java -cp jackson-databind…`）：

```
MismatchedInputException: Cannot construct instance of `OpenArgs` (although at least one
Creator exists): no String-argument constructor/factory method to deserialize from String
value ('/storage/emulated/0/Download/app.apk')
```

也就是安卓上按「打开」**任何**文件都只会拿到 `打开失败：…`。（桌面端走 `open::that_detached`，
没这回事 —— 所以只换移动端那条定义，见 `lib.rs` 里两份 `open_path`。）上游 `v2` 分支与 2.7.0
里这行一模一样，升插件不会修好。

就算参数形状对上也不够：它交给 `ACTION_VIEW` 的是**没有 scheme 的路径**、也不带 MIME ——
系统解析不出任何 activity。

### 怎么做

- Kotlin 侧新插件 `FileOpenPlugin`（`gen/android/…/com/x177plus/orbdrop/`），Rust 侧
  `mobile::open_file` 调它（与 `notify` 那条同款：`register_android_plugin` + 静态句柄 +
  `run_mobile_plugin_async`）。
- 递出去的是 `FileProvider` 的 `content://`：`getUriForFile(activity, "<包名>.fileprovider", file)`
  + `setDataAndType(uri, mime)` + `FLAG_GRANT_READ_URI_PERMISSION`。少了那个读权限，接收方读不了
  这份 URI —— 安装器会当场失败。
- MIME 按扩展名问系统（`MimeTypeMap`），问不到给 `*/*`：让用户自己选"用什么打开"，与安卓惯例
  一致（比"没有应用可执行此操作"有用）。`apk` 先钉死成 `application/vnd.android.package-archive`
  —— 不依赖 ROM 自带那张表里有没有它。
- **"安装"不是另一条路**：那个 MIME 正是系统安装器（PackageInstaller）认领的，`ACTION_VIEW`
  一到就进安装界面。走它、而不是自己开 `PackageInstaller` 会话：后者要自己处理确认 UI 与
  `REQUEST_INSTALL_PACKAGES` 的运行时语义；这里清单声明那条权限只为让
  「设置 → 应用 → 特殊应用权限 → 安装未知应用」**能列出 OrbDrop**（只声明了它的应用才在列表里，
  Android 8 起那个开关默认关着）。首装时系统自己引用户去开一次。
- 手机端界面：收件行 → 文件操作表，`.apk` 的第一项写「安装」、其余写「打开」
  （`FileActionsSheet.svelte` 的 `isApk`）。

### 坑

- **`path="."` 那种根是废的。** 模板原来那两条（`<external-path path="."/>`、`<cache-path path="."/>`）
  写的是 `"."`，而 `File(根, ".")` 不消点段 —— 拼出来是 `<根>/.`；`getUriForFile` 里拿
  `root.getPath()` 做 `startsWith` / `endsWith("/")` 比对，`<根>/.` 谁也匹配不上（会抛
  `Failed to find configured root that contains …`）。所以 `path` **一律不写**（那两条也顺手改掉了）：
  `buildPath` 跳过 null 段，根就是它自己（反编译 androidx 1.13.1 的 `FileProvider` 核对过：
  `root-path → DEVICE_ROOT = File("/")`，`buildPath` 对 null 段直接跳过，`getUriForFile` 用
  `endsWith("/")` 决定取 `substring(len)` 还是 `substring(len + 1)`）。
- **收件目录在应用私有数据目录下**（`app_data_dir` + `OrbDrop/received`），FileProvider 预定义的
  那几个根（`files-path` = `getFilesDir`、`cache-path` = `getCacheDir`、`external-*`）**一个都不覆盖
  它** —— 这是非 `root-path` 不可的原因。怕太宽的话：这个 provider 是 `exported="false"` +
  `grantUriPermissions="true"`，也不是 `DocumentsProvider`（给不出目录枚举），外部只能拿到我们主动
  随 Intent 授出去的那**一个**文件的读权限。
- **文件夹那一档**：`content://` 换不来一个能"浏览"它的应用，丢一个解析不出的 Intent 只会让用户
  看到系统的"没有应用可执行此操作"。所以 Kotlin 里显式拒绝，给一句人话
  （`这是文件夹：安卓上没有能打开应用私有目录的应用`）—— ui 侧拼出来是 `打开失败：…`。
- **前端那条更要命：`onClose()` 之后 props 就读不到了。** `FileActionsSheet` 那三项动作原来是
  `onClose(); await api.openPath(entry.path)` —— 表一关，这个组件的 props 当场变成 null，
  实测界面上只会出一条 `复制路径失败：Cannot read properties of null (reading 'entry')`，
  而「打开/安装」更安静：`entry.path` 在 `await` 求值那一刻就抛，命令**根本没发出去**，
  连 toast 都没有（拒绝没人接）。所以三项动作都改成**先把要用的值取出来、再关表**。
  以前没人撞见是因为后端那条路本来就坏着（上面那个 Jackson 的坑）—— 两个 bug 互相遮住了。
- `invoke.parseArgs` 的字段名就是 Rust 那侧 JSON 的键（这里是 `path`），少一个就抛在 Kotlin 里、
  Rust 只看到一句 reject。

### 校验（真机实测：Meizu 17 / Android 13，界面那条路）

构建与静态检查：`npm run build:mobile` 与 `npm run check`（svelte-check，138 文件 0 错）干净；
`cargo check`（桌面）干净；`npx tauri android build --apk --debug --target aarch64` 与发行包
`npx tauri android build --apk --target aarch64`（R8 + minify）都通过（Rust aarch64 + Kotlin + 清单合并）。
发行包的 `classes.dex` 里 `FileOpenPlugin` / `OpenFileArgs` 都在：keep 规则来自 tauri-android 那份
`proguard-rules.pro`（`@TauriPlugin` 类保 `@Command` 方法与公开构造、`@InvokeArg` 类整个保留）。

**debug 包**（重签成发行密钥后 `adb install -r`，所以 `run-as` 可用，往收件目录里塞了真 APK 与一个 txt）：

1. 收件页出现这两条；点那份 APK → 表里第一项就是**「安装」**（描述"交给系统安装器安装这个 APK
   （首次需先允许 OrbDrop 安装未知应用）。"）；点 `note.txt` 那一档是「打开」+ "用系统应用打开这份文件。"；
2. 点「安装」→ 界面上出 toast **"已交给系统安装器安装「Via-browser.apk」"**，系统安装器随即到前台
   （`topResumedActivity=com.android.packageinstaller/.FlymePackageInstallerActivity`），界面上写着
   **`Via` / 正在安装** —— 它能从 `content://` 里读出包名，说明 FileProvider 的根与那个读权限都对；
   装完 `mark.via` 的 `lastUpdateTime` 变成刚刚、`codePath` 换到新的安装目录、`firstInstallTime` 不变
   （是更新不是重装）；
3. 同一个包里另外两项也过了一遍：「删除本地副本」→ 原生确认框 → OK → 文件从盘上与界面上同时消失；
   「复制路径」仍然是失败的，但已经是**另一件事**：`复制路径失败：Document is not focused.`
   （`navigator.clipboard` 在 webview 里要求文档有焦点；与本条需求无关，没动它）；
4. 落盘之外的几档**不静默**（直接调命令验的）：文件夹 → `这是文件夹：安卓上没有能打开应用私有目录的应用`；
   文件不在 → `文件不在了：<路径>`；非 APK → 系统的"打开方式"选择器（`ResolverActivity`）。

**发行包**（minify 之后同一个包、同一个密钥的升级安装；`run-as` 已不可用，所以全走 `input tap`）：
文件页 → 点 `Via-browser.apk` 那一行 → 表里点「安装」→ 活动栈里出现
`com.android.packageinstaller/.FlymePackageInstallerActivity`，装完 `mark.via` 的 `lastUpdateTime`
再次更新 —— **R8 之后这条路一样通**。
